# SLA с рабочими календарями

Сначала примените миграцию `014_sla_calendars.sql`. Журнал этапов записывается триггерами MySQL при создании задачи, смене этапа и изменении признака завершения этапа. Поэтому учитываются также изменения через API и автоматизации.

В «Администрирование → SLA задач» создайте календарь: часовой пояс IANA, интервалы по дням недели и праздничные даты. Можно задать несколько интервалов с перерывом. Без календаря время считается круглосуточно. Интервалы не должны пересекаться; конец `00:00` в редакторе означает 24:00 текущего дня. Учитываются переходы летнего времени; несуществующая граница при переводе часов вперёд сдвигается вперёд через разрыв. Прогноз даты ограничен ближайшими десятью годами; если рабочих часов недостаточно, дата возвращается как null.

У каждого правила есть ключ таймера. Например, `completion` — выполнение, `approval` — согласование. Первое подходящее правило выбирается отдельно для каждого ключа по позиции, затем ID. Условия применяются к текущим атрибутам задачи. Пустой список запуска означает начало с создания; пустой список завершения — остановку на готовом этапе. Для согласования укажите его этапы запуска и завершения. Паузы не расходуют рабочие минуты.

После повторного открытия можно продолжить накопленное время, начать новый цикл с нуля или оставить таймер завершённым. История содержит все циклы; итоговое время при restart относится к текущему циклу. Закрытие в точности на лимите считается успешным. Момент нарушения сохраняется из рабочего интервала, а не подменяется текущим временем.

В карточке задачи откройте «Как рассчитан SLA»: видны интервалы, паузы, циклы, минуты и версии применённых настроек. Журнал хранит фактические переходы, расчёт выполняется по текущей версии правила и календаря. Изменение настроек пересчитывает прошлые интервалы; это не неизменяемый договорный журнал. Старые переходы до миграции восстановить достоверно невозможно: исходное состояние помечается baseline, а расчёт — приблизительным. Для закрытой старой задачи один раз используется прежний updated_at; последующие правки не меняют зафиксированное завершение.

Правила, использующие скрытые для пользователя атрибуты, не возвращаются в его SLA-отчёте. История задачи требует доступа к её проекту. Календари требуют `sla.manage` и браузерной сессии. Редактор календаря и правил проверяет ревизию и возвращает 409 при конфликте.

Методы: `GET/POST /api/work/sla/calendars`, `PATCH/DELETE /api/work/sla/calendars/{id}`, `GET /api/work/sla/tasks/{id}`. Прежние `/api/admin/task-sla` сохраняются; добавлены `counter_key`, `calendar_id`, `revision`, `config.start_stage_ids`, `config.stop_stage_ids`, `config.pause_stage_ids`, `config.reopen` (`resume`, `restart`, `keep`). Интервалы календаря передаются минутами от полуночи, дни — от 0 (воскресенье) до 6.
