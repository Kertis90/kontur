# Планирование и рабочие инструменты — 0.10.0

Новые разделы открываются через **Планирование и инструменты** в боковом меню. Конструктор правил находится в **Администрирование → Автоматизация**. Функциональные разрешения назначаются через существующие роли пользователей и групп; администратору доступны все инструменты своего рабочего пространства.

## Автоматизация

Создайте правило, выберите проект и событие: создание/изменение задачи, комментарий, приближение срока, завершение согласования или расписание. Для расписания задаётся интервал от 5 минут до года.

В конструкторе можно объединять условия «Все»/«Любое», добавлять ветви «Да»/«Нет», менять порядок действий, отправлять уведомления, изменять поля задачи и создавать подзадачи. Поддерживается до 100 блоков и 5 уровней вложенности.

Выберите задачу и нажмите пробный запуск: результат показывает выбранную ветку и действия, ничего не записывая в задачи. Реальные запуски видны в журнале со статусом и результатами шагов. Правило выполняется от имени последнего редактора с его актуальными правами; отключение сотрудника прекращает выполнение. Изменения одного запуска и отметка обработки события сохраняются транзакционно. Цепочки правил ограничены пятью переходами.

После обновления проверьте старые правила пробным запуском. Поддерживаемые действия перечислены в API; произвольные legacy-действия не исполняются новым движком.

## Согласования

Создайте запрос по проекту или конкретной задаче. Выберите последовательное либо параллельное рассмотрение, согласующих, заместителей и срок. Инициатор не может согласовать собственный запрос. Решения требуют комментария и сохраняются в истории. Для решения нужны одновременно назначение в запросе и разрешение `approval.decide`.

В настройке переходов отметьте этапы, требующие согласования, и обязательные поля. Согласование привязано к версии задачи: изменение содержимого после проверки требует нового запроса. Нельзя одновременно подменить согласованное содержание и перевести задачу на защищённый этап. Проверка действует для карточки, канбана, массовых изменений, API и автоматизаций.

Worker напоминает о приближении срока. В последовательном запросе уведомляется текущий согласующий; в параллельном — все ещё не принявшие решение. Срок сам по себе не подменяет решение человека.

## Загрузка и портфель

В загрузке задайте рабочую неделю сотрудника, частичную занятость, отпуск, отсутствие либо общий выходной. Распределите часы сотрудника по проектам. Красным показано превышение доступных часов. Отпуск уменьшает доступность, но не удаляет уже запланированную работу. Пересекающиеся отсутствия учитываются по максимальному проценту недоступности. Часы — ручной план; система не выводит их автоматически из оценок задач.

Занятость в недоступном проекте входит в общий итог, его название скрыто. Сам раздел загрузки требует отдельного разрешения рабочего пространства.

В портфеле доступны блокирующие связи между задачами разных проектов, расчёт критического пути, сдвиг проектов в сценарии и сравнение с базовым планом. Зависимость задаётся в направлении «эта задача зависит от другой». Циклические связи отклоняются.

Сценарий не меняет реальные сроки. Расчёт использует календарные дни и зависимости «завершение → начало», не выполняет автоматическое выравнивание ресурсов. Задачи без обеих дат исключаются из расчёта длительности; перед использованием критического пути заполните даты. Сохранённый базовый план при чтении фильтруется по текущим правам пользователя.

## Записи и поручения встреч

Откройте **Результаты встреч**, выберите доступную запись и получите расшифровку через существующий раздел записей. Затем запустите выделение поручений. Обработка идёт в фоне и показывает прогресс. Можно продолжать работу в других разделах.

ИИ предлагает название, описание, исполнителя, срок и точную цитату из расшифровки. Если исполнитель не определён, поле остаётся пустым. Список кандидатов ограничивается именами, найденными в тексте, чтобы большие встречи не переполняли контекст модели. Предложения нужно проверить вручную: только подтверждение создаёт задачу. Повтор подтверждения уже принятого поручения не создаёт дубль. Подтверждённые поручения можно перенести в черновик статьи выбранного пространства.

Время у цитаты обозначает начало фрагмента расшифровки, а не точную секунду произнесения фразы. Текущая нарезка — до десяти минут на фрагмент. Поиск по тексту и главы позволяют переходить к соответствующей части видео. Организатор с правом управления может добавить главы, исправить текст и назначить срок хранения. При конфликте исправления одного фрагмента сервер требует обновить его.

По истечении срока запись становится недоступной сразу; worker удаляет объект S3, расшифровку и историю её исправлений. Созданные задачи, статьи и уже извлечённые поручения — самостоятельные рабочие материалы, автоматически они не удаляются. Исправление расшифровки изменяет её ревизию для будущих запросов ИИ; существующие сводки не переписываются задним числом.

## Поиск с ИИ

Ассистент ищет по доступным задачам, статьям и завершённым расшифровкам, затем отвечает со ссылками на источники. Права проверяются до поиска и после генерации; ответы не кэшируются между пользователями. Запросы входят в общую дневную квоту ИИ.

В этой версии модель подбирает ключевые слова и фразы, а поиск выполняется по тексту MySQL. Это не векторный индекс: смысловые синонимы без совпадения в тексте могут не находиться. Выборка и контекст ограничены; уточняйте названия проекта, встречи или термин. Ассистент не изменяет проекты и не выполняет инструкции из найденных документов.

## Совместная база знаний

Откройте статью и нажмите **Совместно и история**. Существующий визуальный редактор остаётся доступен. Совместная работа использует отдельные текстовые блоки Markdown: изменения разных блоков сохраняются независимо, для одного и того же блока показывается конфликт. Автоматического посимвольного слияния нет.

Видны присутствующие редакторы, комментарии к статье или блоку, цитаты и решённые замечания. История хранит снимки изменённых версий с момента обновления до 0.10. Можно назначить ответственного и дату следующего пересмотра, отправить статью на проверку и опубликовать согласованную версию. Изменение содержимого статьи с ответственным возвращает её в черновик. Доступ по-прежнему определяется пространством и командой.

## Доступ к полям и временные права

В разделе **Доступы** можно ограничить чтение и редактирование пользовательского атрибута пользователями и группами. Вложенные группы учитываются. Поле без политики использует обычные права задачи; политика с пустыми списками закрывает его для обычных участников. Редакторы автоматически получают чтение. Администраторы и менеджеры доступа сохраняют полномочия на настройку и просмотр.

Закрытые атрибуты удаляются из текущих значений и истории API-ответов, а не только скрываются в форме. SLA-показатели, зависящие от закрытых полей, исключаются из выдачи. Эти ограничения относятся к пользовательским атрибутам, не к произвольному тексту описаний, сообщений или комментариев.

Запрос временного доступа можно создать по известному ключу проекта. Доступ выдаётся после решения менеджера, максимум на 90 дней. Нельзя одобрить свой запрос либо выдать отсутствующие у себя разрешения. Явный запрет роли имеет приоритет. Раздел объяснения доступа показывает прямые назначения, группы, функциональные роли и временные разрешения.

## Офлайн и личные уведомления

Включите офлайн-режим в личных инструментах, пока сеть доступна. На устройстве сохраняется минимальный контекст задач. Можно подготовить новую задачу, изменение приоритета, текстовый либо голосовой комментарий. Это режим черновиков, а не полная работа канбана и конференций без сети.

После восстановления сети выполните синхронизацию. Сначала проверяется исходная учётная запись, затем отправляются изменения. Для изменившейся задачи можно сравнить локальное изменение с текущей версией и явно выбрать результат. Сервер не создаёт повторные объекты при повторе того же идентификатора операции. Очередь обновляется атомарно, в поддерживающих Web Locks браузерах синхронизация согласована между вкладками.

Голос записывается локально, до 30 минут и примерно 24 МБ на устройстве; серверный предел файла — 25 МБ. После загрузки используется существующий механизм голосовых комментариев и общей кэшируемой расшифровки. Для микрофона и установки PWA нужен HTTPS либо локальный доверенный адрес. Выход из аккаунта удаляет локальные копии и неотправленные черновики.

В настройках уведомлений выберите часовой пояс, тихие часы, ежедневный/еженедельный дайджест или доставку без дайджеста. Почтовые уведомления включаются отдельно и требуют SMTP. В письма попадают только поддерживаемые уведомления о доступных задачах, встречах, статьях и согласованиях. При аварии между отправкой SMTP и фиксацией результата возможно повторное письмо.

## Импорт и разработка

Импорт поддерживает CSV с запятой и Jira JSON с массивом `issues`: до 1000 задач и 2,5 МБ. Сопоставьте поля и этапы, посмотрите ошибки и повторы, затем подтвердите. После изменения соответствий повторите предварительный просмотр. Подтверждение проверяет его контрольную сумму; ошибки отменяют весь пакет. Внешние ключи защищают от повторного импорта. Вложения, комментарии, история Jira и её произвольные пользовательские поля не переносятся этой версией импортера.

Массовое изменение работает с приоритетом, этапом, исполнителем, сроком, оценкой и готовностью до 100 задач. Проверки версий и прав выполняются для всего пакета в одной транзакции.

Подключение разработки возвращает URL webhook и одноразово отображаемый секрет. В GitHub используются push, pull request, workflow/check run события; в GitLab — push, merge request и pipeline. Укажите ключ задачи в названии ветки, коммите или запросе слияния. Связи и состояние сборок появятся в карточке задачи. Текст описания релиза собирается из его задач и допускает правку перед копированием.

Проверка подписи соответствует [протоколу GitHub](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) и [webhook GitLab](https://docs.gitlab.com/user/project/integrations/webhooks/). Для GitHub передаётся HMAC-SHA256 исходного тела в `X-Hub-Signature-256`, для GitLab — секрет в `X-Gitlab-Token`.

## Разрешения и API

| Возможность | Функциональное разрешение | API scope |
| --- | --- | --- |
| Правила и журналы | `automation.manage` | `automation:read` / `automation:write` |
| Запрос и решение согласования | `approval.request` / `approval.decide` | `tasks:write` |
| Ограничения переходов | `approval.manage` | `projects:write` |
| Загрузка | `capacity.view` / `capacity.manage` | `projects:read` / `projects:write` |
| Базовые планы | `portfolio.manage` и `report.view` | `projects:write` |
| Межпроектные связи | `task.edit` и доступ к обоим проектам | `projects:write` и `tasks:write` |
| Поиск ИИ | `ai.search` | `ai:write`, `tasks:read`, `knowledge:read`, `conference:read` |
| Поручения по записи | права ИИ и просмотра записи | `ai:read` / `ai:write` |
| Подтверждение поручения | дополнительно `task.create` | дополнительно `tasks:write` |
| Статья из поручений | редактирование пространства | дополнительно `knowledge:write` |
| Доступ к атрибутам | `project.access.manage` | `projects:write` |
| Офлайн и массовое изменение | права соответствующей задачи | `tasks:write` |

Scopes автоматизации не добавляются существующим персональным токенам автоматически. Администратор разрешает их пользователю, после чего пользователь выпускает подходящий токен. Полный перечень методов с JSON-примерами доступен в **Мой API**, [справочнике API](API.md) и `GET /api/openapi.json`.
