# Обзор и предложения по развитию — 22 сентября 2026

Обзор Контур Work 0.18.0 подготовлен перед первой публикацией в
`https://github.com/Kertis90/kontur.git`. Пользователь выбрал постепенный
переход с Jira в Контур. Ниже описаны предложения; новые функции в рамках
этой публикации не реализуются.

## Что представляет собой проект

Это приложение для самостоятельного размещения внутри организации: проекты,
задачи, доски, спринты, планы, база знаний, чаты, встречи и инструменты ИИ.
Уже есть согласования, цели, тестирование и Allure, уведомления, подключения
корпоративного входа, второй фактор и управление сессиями.

Интерфейс построен на Next.js 16 и React 19. Сервер и фоновые процессы используют
Node.js; основные данные находятся в MySQL 8.4, очереди — в Redis, файлы — в S3.
Встречи обслуживает LiveKit. В поставке есть Docker Compose и Helm.
Подробная карта файлов сохранена в [HANDOFF.md](HANDOFF.md).

Сильные стороны основы: разграничение доступа на сервере, журнал действий,
продолжение прерванных работ, проверка прав при фоновой обработке, шифрование
настроек подключений и приватное хранение файлов. Эти механизмы следует
сохранять при расширении импорта. Наличие кода не заменяет проверку на реальных
MySQL, S3, корпоративном входе и медиасервере.

## Что уже есть для Jira

Существуют два пути: обычный импорт CSV/Jira JSON и расширенный перенос Jira.
Для переезда следует развивать расширенный путь, описанный в
[JIRA-IMPORT.md](JIRA-IMPORT.md), а не создавать третий независимый импорт.

| Возможность | Состояние по коду |
| --- | --- |
| Название, описание, статус, приоритет, исполнитель и срок | Переносятся с сопоставлением этапов; сотрудник должен существовать в Контуре |
| Комментарии и история | Сохраняются с исходными авторами и датами; неполный экспорт отмечается предупреждением |
| Файлы | Описание берётся из JSON, сами файлы загружаются отдельно с проверкой размера и SHA-256 |
| Связи | Поддерживаются известные типы; циклы и неизвестные связи попадают в предупреждения |
| Пробная проверка и продолжение | Есть предварительный просмотр, подтверждение и продолжение с сохранённой позиции |
| Повторный перенос | Существующий внешний ключ пропускается; задача, история и файлы не обновляются |
| Чтение непосредственно из Jira | Подключения Jira в каталоге и в механизме внешней синхронизации нет |
| Крупный переезд | Один расширенный пакет ограничен 500 задачами и 2,5 МБ; автоматической подготовки пакетов нет |

Основания: `src/lib/work-import.js`, `work-jira-import.js`,
`jira-import-model.js`, `external-sync.js`, `integration-catalog.js`;
проверки — `scripts/import-operations.test.mjs`.

Дополнительные ограничения для переезда:

- Исполнитель определяется по email или отображаемому имени. Нужна явная таблица
  соответствий, особенно при одинаковых именах и недоступных email.
- Основной набор полей не переносит типы задач, эпики и родительскую иерархию,
  спринты, версии, компоненты, оценки, трудозатраты и произвольные поля Jira.
  Наличие этих возможностей в самом Контуре не означает поддержку их импорта.
- Описание Jira преобразуется в простой текст: оформление и встроенные элементы
  требуют отдельной проверки на реальных примерах.
- Связь с задачей из следующего пакета не достраивается автоматически;
  межпроектные связи требуют отдельной обработки.
- Старый внешний ключ уникален внутри проекта назначения, без отдельного
  обозначения исходного сервера Jira. Для нескольких источников этого недостаточно.

## Рекомендуемые улучшения

| Очерёдность | Улучшение | Польза и критерий готовности |
| --- | --- | --- |
| 1 — до переезда команды | Повторяемая проверка поставки | Автоматические тесты, quality и сборка на Node.js 22; проверка обновления отдельной MySQL и восстановления копии; браузерные проверки входа, задач и прав |
| 2 — основной продуктовый приоритет | Мастер переезда с Jira | Один выбранный проект переносится с файлами и понятным отчётом; повторный запуск не создаёт дубли и не теряет изменения |
| 3 — вместе с пилотом | Удобный первый запуск | Последовательность «организация → сотрудники → проект → импорт → первая задача», короткие объяснения прав и понятные сообщения об ошибках |
| 4 — после пилота | Быстрая ежедневная работа | Измерить открытие доски, поиск, сохранение задачи и работу на телефоне; улучшать обнаруженные задержки и неудобства |
| 5 — постоянно | Более простое сопровождение | Постепенно разделять крупные обработчики и экраны на небольшие части с проверками поведения и русскими комментариями над изменёнными методами |

В составе исходников нет `.github/workflows` и настройки браузерных тестов.
`npm run quality` проверяет выбранные правила CSS, поставку и договорённости API,
но не является полной проверкой качества JavaScript. Предлагается начать с
автоматизации уже существующих команд, затем добавить проверки самых частых
действий пользователя и правил доступа. Настройки GitHub Actions и защиты ветки
в этой публикации не изменяются.

Для ускорения программы сначала нужны измерения на реалистичном объёме данных.
Оснований обещать определённую скорость или вместимость по одному чтению кода нет.
Главный обработчик API `app/api/[[...path]]/route.js` занимает около 211 КБ,
`app/page.jsx` — около 86 КБ: их постепенное разделение упростит изменения,
но само по себе не доказывает ускорение приложения.

Мониторинг, резервирование, второй фактор и поиск по смыслу уже существуют.
Приоритет — проверить их на стенде, упростить настройку и устранить обнаруженные
проблемы. Отдельный Service Desk не предлагается: он исключён из продукта.

## Как развивать переезд с Jira

### Этап 1. Пилот на одном проекте

Собрать небольшой представительный набор: обычная задача, эпик, подзадача,
нестандартные статусы, одинаковые имена сотрудников, ограниченные данные,
комментарии, файлы и связи. Показать перед переносом, что будет перенесено,
что потребует сопоставления, а что пока не поддерживается.

Сохранить таблицы соответствий сотрудников, этапов, типов задач и полей.
Отдельно сопоставить группы и доступы: перенос содержимого не должен автоматически
расширять круг читателей. Для ограниченных задач, комментариев и полей сначала
проверять возможность сохранить ограничения; иначе исключать их из переноса
с явным отчётом до отдельного решения владельца.

### Этап 2. Подключение к Jira

Добавить чтение выбранных проектов непосредственно из Jira, автоматическую
подготовку небольших пакетов и загрузку файлов. Первое подключение должно
запрашивать доступ только к чтению необходимых данных Jira. Секреты хранить
существующим механизмом шифрования; права исполнителя проверять перед каждой
фоновой операцией. Для закрытой сети сохранить режим подготовленного экспорта.

Jira Cloud и Jira Data Center следует поддерживать отдельными вариантами
подключения. В Cloud для нового поиска учитывать `/rest/api/3/search/jql`;
прежние методы `/rest/api/3/search` в документации отмечены как удаляемые.
Источник: [официальный поиск задач Jira Cloud](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/).
Для Data Center предусмотреть поддерживаемую установленной версией авторизацию;
Atlassian описывает персональные токены для внешних подключений:
[Personal access token](https://developer.atlassian.com/server/jira/platform/personal-access-token/).

Получать все страницы задач, комментариев и истории. Обрабатывать сетевые сбои,
ограничения запросов и указанную сервером задержку повторной попытки.
Эти требования нужны и при разовом большом переносе:
[ограничения запросов Jira Cloud](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/).
Для файлов разрешать только проверенные адреса выбранной Jira и явно разрешённого
хранилища; учитывать перенаправления без передачи credentials посторонним узлам.
Нельзя превращать импорт в скачивание произвольных URL из пользовательского JSON.

### Этап 3. Повторный перенос изменений

До переключения конкретного проекта источником актуальных данных остаётся Jira.
Контур используется для проверки переноса; обычное редактирование перенесённых
задач на этом этапе следует ограничить согласованным режимом проекта.

Сохранять исходный сервер, стабильный идентификатор задачи Jira, её ключ,
соответствие задаче Контура и отметку последней успешно перенесённой версии.
Если локальные изменения уже есть, показать различия и запросить выбор для
конфликтующих полей. Не перезаписывать изменения сотрудников молча.

Повторять получение изменений с небольшим перекрытием по времени и устранять
повторы по идентификаторам и сохранённым версиям. Отсутствие задачи в поисковой
выдаче само по себе не означает удаление: могли измениться права или фильтр.
Повторный запуск после сбоя должен продолжать работу без повторных задач,
комментариев и файлов. После всех пакетов выполнять общий проход по связям.

### Этап 4. Переключение проекта

1. Согласовать окно завершения работы в Jira для выбранного проекта.
2. Выполнить последний перенос изменений и общий проход по связям.
3. Сверить задачи по исходным идентификаторам, комментарии, историю, файлы,
   связи, сотрудников и доступы. Показать отсутствующие и неподдержанные данные.
4. Получить подтверждение владельца проекта по отчёту.
5. Открыть работу команды в Контуре, остановить обновление этого проекта из Jira
   и оставить Jira доступной для чтения на согласованный срок.

Проекты можно переносить по очереди. После начала работы в Контуре возврат
в Jira потребует отдельного переноса новых изменений; восстановление старой
копии не является безопасным универсальным откатом.

Двустороннюю синхронизацию имеет смысл рассматривать только при длительной
обязательной работе в двух системах. Для выбранной цели она добавляет правила
разрешения конфликтов и удлиняет переезд.

## Что уточнить перед реализацией

- Jira Cloud или Data Center, версия и доступность из сети Контура.
- Число проектов и задач, объём файлов и истории, ограничения доступа.
- Обязательные поля, типы связей, спринты и сторонние расширения Jira.
- Требуется ли отдельно переносить Confluence: текущий импорт Jira этого не делает.
- Пилотный проект, ответственный за приёмку и допустимое окно переключения.

Это следующий этап работ. Реальное подключение к Jira, перенос данных,
обновление базы и развёртывание приложения здесь не выполнялись.
