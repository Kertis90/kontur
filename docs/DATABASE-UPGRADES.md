# Обновление схемы MySQL

Это руководство относится к MySQL. Для новой установки PostgreSQL в 0.22
используется отдельная последовательность атомарных миграций с проверкой
контрольных сумм и журналом ошибок: [DATABASES.md](DATABASES.md).

`node scripts/migrate.mjs` использует отдельное соединение и именованную блокировку, привязанную к имени базы. При запуске нескольких реплик только одна применяет схему; ожидание другой ограничено 50 секундами. Блокировка автоматически исчезает при потере соединения. Требуется один primary MySQL: именованные блокировки локальны серверу и не координируют разные writable primary.

Перед выполнением SQL фиксируется `schema_migration_runs.status=running` с SHA-256 файла. Успешное завершение атомарно отмечается в этом журнале и `schema_migrations`. При сбое остаётся `failed` или `running`, и последующие старты прекращаются до восстановления. Проверяемые исключения — исходные миграции `013` (с 0.11.1) и `021` (с 0.14.1), описанные ниже. Изменённые контрольные суммы и попытка запустить старый код, в котором отсутствуют уже применённые миграции, также останавливают обновление.

Обёртка `BEGIN/ROLLBACK` не отменяет группу DDL-команд MySQL: ALTER/CREATE выполняют неявный commit. Поэтому скрипт не сообщает, что неудачная миграция полностью откатилась. См. [правила неявного commit](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html) и [область действия GET_LOCK](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html).

## Существующие установки

Для миграций, уже записанных старым скриптом в `schema_migrations`, при первом обновлении принимается контрольная сумма файлов поставки и статус `adopted`. Это исходная точка последующей проверки, не доказательство того, что исторический файл или схема раньше совпадали с поставкой. Перед обновлением сравните схему на тестовом восстановлении.

В Compose остаётся отдельный сервис migrate, в Helm — pre-install/pre-upgrade Job. Приложение, оба worker и мигратор должны использовать одну версию образа. При длительном обновлении второй мигратор завершится с ошибкой ожидания; после успешного первого запуска его можно штатно повторить. Незавершённые миграции, кроме проверяемого восстановления исходных `013` и `021`, обычный повтор не обходит.

## Диагностика без изменения БД

```sh
npm run db:status
# Или внутри образа, используя окружение мигратора:
node scripts/migrate.mjs --status
```

Команда только читает метаданные MySQL и журналы. Вывод JSON содержит `migrations[].error_code`, статус, совпадение SHA-256, `server.binary_logging`, `server.trust_creators`, а для незавершённых `013` и `021` — соответственно `recovery_013` и `recovery_021` с полями `present`, `missing` и `conflicts`. Если старый процесс был аварийно убит, код ошибки может отсутствовать. Данные пользователей, сессий, настройки и секреты интеграций не читаются. Это диагностический снимок; при параллельной миграции он может измениться. Для согласованной проверки запускайте его в окне обслуживания без другого мигратора.

## Ошибка «021_integrations.sql прервана (ER_TABLE_EXISTS_ERROR)»

Ошибка означает, что при CREATE TABLE уже существует объект с таким именем. В поставке обнаружен конфликт: `002_platform_modules.sql` уже создаёт `integration_connections` для старых настроек рабочего пространства, а `021` создаёт под тем же именем другую таблицу проектных уведомлений, затем `integration_deliveries`. Характерные отличия схемы 002 — `provider VARCHAR(80)`, `name VARCHAR(180)`, `secrets_encrypted`, `last_sync_at`, даты TIMESTAMP и отсутствие `project_id`. Это ошибка поставки, а не признак повреждения пользовательской базы.

В **0.14.2** мигратор исправляет этот переход. Версия 0.14.1 умела продолжать только частично созданную новую схему 021 и правильно останавливала несовпадение, но не устраняла конфликт с 002. Используйте 0.14.2. Восстановление по-прежнему привязано к исходному файлу `021_integrations.sql` с SHA-256 `1fa7890a7e3ced002c2f5cf98c8408760a76885e1e61e47eab0c85189333b3e8`. Ни один файл 001–029 не изменён. Под именованной блокировкой сначала проверяются контрольная сумма и последовательность журналов, затем таблицы и родительские ключи `workspaces`, `projects`, `users`.

- Сверяются InnoDB, столбцы, NULL/default, AUTO_INCREMENT, обновляемые даты, точный состав и порядок ENUM, кодировка utf8mb4, сопоставления строковых столбцов, первичные/уникальные/поисковые индексы, внешние ключи и действия удаления/обновления. Неожиданные CHECK и триггеры блокируют восстановление. Дополнительные неуникальные индексы допустимы, в том числе автоматически созданные MySQL для внешних ключей.
- При любом конфликте существующие таблицы не изменяются и недостающие не создаются. `--status` показывает причину в `recovery_021.conflicts`. Код `KONTUR_INTEGRATION_SCHEMA_CONFLICT` означает, что требуется разбор отличий с DBA.
- Если распознана точная схема 002, её таблица сохраняется командой RENAME TABLE под именем **`integration_connections_legacy_002`**, затем создаются две таблицы из исходной 021. Строки, идентификаторы, настройки и шифротекст не преобразуются и не удаляются. Занятое имя сохранения, несовместимая старая структура, неожиданные входящие внешние ключи, зависимые представления или уже существующая `integration_deliveries` рядом со старой схемой блокируют переименование до DDL. [Семантика и права RENAME TABLE](https://dev.mysql.com/doc/refman/8.4/en/rename-table.html).
- Если схема уже новая, создаются только отсутствующие таблицы; очередь доставок и её статусы сохраняются. Если обе новые таблицы уже созданы, достаточно сверки без DDL. Сохранённая таблица 002, если она есть, тоже проверяется. После итоговой проверки миграция атомарно отмечается в обоих журналах.
- Повторное прерывание восстанавливается тем же способом. Более поздние применённые миграции после незавершённой `021` и изменённый SHA-256 остаются блокирующими условиями. Успешно зарегистрированная `021` повторно не исполняется.

`--status` дополнительно показывает `recovery_021.legacy`: `rename_pending` — схема 002 проверена и будет сохранена, `preserved` — таблица уже переименована, `blocked` — требуется разбор конфликта. `--status` сам таблицы не переименовывает. После обрыва между RENAME и CREATE повторный запуск использует уже сохранённую таблицу, без повторного переименования. Общая блокировка мигратора не заменяет остановку приложения, worker и сторонних изменений схемы на время обновления.

Старые настройки видны пользователю с правом `integration.manage` в «Интеграции → Ранее созданные webhooks и API → Сохранённые подключения прежней версии». Это перечень прежних подключений; конфигурация и секреты остаются в БД. Автоматической конвертации в проектные уведомления нет: в старой схеме отсутствуют проект и события, а provider имеет произвольное значение. Новое подключение нужно настроить через каталог. Загрузка администрирования исправлена: старые столбцы больше не запрашиваются из новой таблицы 021. Если в ранее вручную исправленной установке сохранённой таблицы нет, список пуст и администрирование продолжает работать.

Для существующего Compose: сохраните резервную копию и исходный лог, замените код версией **0.14.2 в прежнем каталоге установки**, сохранив `.env`, тома и имя Compose-проекта (тот же `-p`, если он использовался). Не запускайте новый каталог архива как другой Compose-проект и не выполняйте `down -v`.

```sh
docker compose stop app worker recording-worker
docker compose build migrate
docker compose up -d --wait mysql
docker compose run --rm --no-deps --entrypoint node migrate scripts/migrate.mjs --status
docker compose run --rm --no-deps --entrypoint node migrate scripts/migrate.mjs
docker compose up -d --wait
```

Выполняйте команды последовательно, останавливаясь при ошибке. До запуска миграции `recovery_021.conflicts` должен быть пуст, а `checksum` — `ok` либо `untracked`, если подробного журнала ещё нет. Отсутствие `recovery_021` при состоянии `applied/adopted` означает, что восстановления не требуется. `build migrate` собирает общий образ приложения и worker; если override задаёт им разные образы, обновите все. Мигратор после восстановления `021` применит и остальные ожидающие файлы, включая `022–029`; последний `up` выполнит штатный seed. После обновления снова проверьте `--status` и экран интеграций.

В Kubernetes соберите и загрузите в свой registry образ 0.14.2, обновите image.tag/chart и используйте прежние values и секреты. До pre-upgrade Job остановите запись приложения и worker; hook сам по себе этого не делает. Диагностика — `node scripts/migrate.mjs --status` в этом же образе с окружением мигратора. Для переименования нужны ALTER/DROP исходной таблицы и CREATE/INSERT на новом имени в той же БД; стандартный пользователь Compose с правами на базу их имеет. При выдаче прав отдельно на каждую таблицу обновите их для сохранённого имени. Глобальные права MySQL или изменение `log_bin_trust_function_creators` для этого исправления не требуются. Сначала проверьте восстановление на копии базы.

## Ошибка «013_sessions_and_directory.sql не завершена»

Сообщение означает наличие незавершённой записи, а не конкретную причину первого сбоя. В прежнем Compose выявлен вероятный источник: `013` первой создаёт триггеры, а MySQL с включённым binlog и `log_bin_trust_function_creators=0` может отклонить их создание обычным пользователем базы с кодом `ER_BINLOG_CREATE_ROUTINE_NEED_SUPER` (1419). Таблицы, созданные перед триггерами, при этом уже сохранены. Подтверждайте причину по `--status` или первоначальному журналу. [Правила MySQL для триггеров и binlog](https://dev.mysql.com/doc/refman/8.4/en/stored-programs-logging.html).

В Compose 0.11.1 для MySQL добавлен `--log-bin-trust-function-creators=1`. Это конфигурация сервера при запуске. Мигратор не выдаёт себе глобальные права и не выполняет `SET GLOBAL`. Перед другими новыми миграциями с триггерами, в том числе `014`, проводится предварительная проверка этой настройки. После исправления конфигурации `013` можно повторить штатной командой миграции.

Алгоритм восстановления действует только для файла `013_sessions_and_directory.sql` с SHA-256 `ec568201f8c33552033dffaa39fb2b069f273cdcbf9a7438143d908e7af4dac4`:

1. Под общей блокировкой проверяются контрольные суммы и порядок журналов. Поздние применённые миграции после незавершённой `013` блокируют восстановление.
2. Через `information_schema` сверяются пять таблиц, типы/NULL/default столбцов, индексы, внешние ключи, дополнительные ограничения CHECK, два столбца `users` и определения двух триггеров. При конфликте изменения схемы не начинаются.
3. Создаются только отсутствующие объекты. Существующие таблицы и строки не удаляются и не переписываются. Два отсутствующих столбца `users` могут добавляться по отдельности; прерывание между ними также восстанавливается.
4. Полная повторная сверка должна подтвердить итоговую схему. Только затем обе записи журналов фиксируются как завершённые. При повторном сбое остаётся незавершённая запись; следующий запуск снова проверяет фактическую схему.

Тот же алгоритм обслуживает первую установку `013` и частичный сбой старого мигратора, у которого ещё не было подробного журнала. Окончательно применённые `013` при обычном запуске заново не исполняются. Исходный SQL-файл не изменён. Режима «игнорировать ошибки», удаления маркеров или слепой отметки «применено» нет.

### Обновление существующего Docker Compose

Сначала сохраните проверенную резервную копию и исходный журнал ошибки. Замените код и Compose на 0.11.1 **в существующем каталоге установки**, сохранив `.env`, имя Compose-проекта и тома. Если используется `-p`, указывайте то же имя во всех командах. Запуск из нового каталога архива с другим именем проекта может подключить другие пустые тома. Не выполняйте `down -v`.

```sh
docker compose stop app worker recording-worker
docker compose build migrate
docker compose up -d --wait mysql
docker compose run --rm --no-deps --entrypoint node migrate scripts/migrate.mjs --status
docker compose run --rm --no-deps --entrypoint node migrate scripts/migrate.mjs
docker compose up -d --wait
```

`up mysql` пересоздаст контейнер при изменении его команды и применит новый параметр, сохранив существующий том. `restart mysql` недостаточен для изменения конфигурации контейнера. `build migrate` собирает общий образ, которым пользуются app, worker и recording-worker. Если вы применяете собственный override с разными образами, обновите их все. Выполняйте следующую команду только после успешного завершения предыдущей. Последний `up` также выполняет штатный сервис migrate/seed перед приложением.

Если `conflicts` не пуст или получен другой код ошибки, автоматическое восстановление не следует обходить: сохраните вывод диагностики и передайте DBA. Код `KONTUR_TRIGGER_PREREQUISITE` означает, что ожидаемая настройка сервера ещё не применена.

### Kubernetes / внешняя MySQL

Chart не управляет внешним сервером MySQL. DBA должен настроить `log_bin_trust_function_creators=1` через конфигурацию сервера или параметр управляемой БД, либо запускать миграцию отдельно разрешённой учётной записью с необходимыми правами. Приложению не следует выдавать глобальный `SUPER`. Обновите общий образ и chart до 0.11.1, сохраните свои значения и секреты, затем повторите pre-upgrade Job. Перед миграцией приостановите запись приложения и worker; Helm hook сам по себе не останавливает старые реплики. Диагностика запускается из того же образа командой `node scripts/migrate.mjs --status` с теми же MySQL env/TLS/secret, что у Job. [Требования CREATE TRIGGER](https://dev.mysql.com/doc/refman/8.4/en/create-trigger.html).

## Изолированный интеграционный сценарий

```sh
docker compose -f deploy/tests/mysql-recovery.compose.yaml up --build --abort-on-container-exit --exit-code-from recovery-test
docker compose -f deploy/tests/mysql-recovery.compose.yaml down
```

Этот отдельный Compose использует одноразовую MySQL 8.4 на tmpfs, внутреннюю сеть без портов хоста и тестовые учётные записи. Он не передаёт контейнерам production-секреты и не подключает рабочие тома. Сценарий воспроизводит ошибки 1419 и 1050 (`ER_TABLE_EXISTS_ERROR`) на таблице, фактически созданной миграцией 002; проверяет отказ при несовпадении старой схемы, обрыв после реально завершённого RENAME, сохранность старых строк и зашифрованных настроек, продолжение частично созданной новой 021, фактический отзыв сессии и API-токена триггерами, все последующие миграции и повторный запуск. Для имитации сбоя перед фиксацией журнала сценарий меняет только журнал одноразовой тестовой БД; производственный мигратор записей не удаляет. Скрипт изменяет глобальный параметр только этой одноразовой тестовой MySQL. Его нельзя переносить в production-контейнер MySQL.

В `deploy/tests/expansion.compose.yaml` дополнительно предусмотрены чистая установка всей цепочки 001–029, seed и загрузка данных администрирования через `getBootstrap` на настоящей MySQL. Оба сценария включены в поставку.

В среде подготовки релиза нет Docker/MySQL; этот интеграционный сценарий включён в поставку, но здесь не выполнялся. Локальные тесты восстановления используют модель ответов драйвера. Проверка на настоящем сервере остаётся отдельным обязательным шагом перед production-обновлением.

## Восстановление после сбоя

1. Сохраните состояние проблемной базы и журналы. Остановите повторные обновления и запись приложения.
2. Проверьте `schema_migration_runs`, `schema_migrations` и фактически созданные столбцы, индексы, ограничения и триггеры. Некоторые команды файла могли завершиться.
3. Предпочтительный путь — восстановление проверенной копии до обновления в отдельную базу, затем устранение причины и повторный прогон всего обновления на ней. Переключение приложения выполняется после проверки данных и доступа.
4. Если DBA вручную завершает частично применённый файл, он должен сверить все его SQL-операции и синхронизировать обе записи журналов в одной транзакции, сохранив точный SHA-256 исходного файла. Простое удаление маркера `failed` не исправляет схему и не поддерживается как автоматический режим.

Не запускайте старый образ после применения новых миграций без проверенного плана восстановления. Резервировать нужно MySQL, S3 и секреты шифрования вместе; журнал миграций не заменяет резервные копии. PITR и восстановление на целевом стенде пока не реализованы и не проверены этой поставкой.

## Обновление 0.18.0: ИИ и постоянные комнаты

`034_agent_workbench.sql` добавляет признак служебного пользователя и таблицы учётных записей исполнения, публикаций/черновиков, сохранённых согласований, генераций, наборов и пакетов оценки ИИ. `035_chat_rooms.sql` добавляет метаданные постоянных комнат и приглашения. Старые каналы и сообщения не преобразуются: комната создаётся отдельной записью поверх существующего `chat_channels`, поэтому история сохраняется. Создание комнаты не добавляет участника автоматически.

Файлы 001–033 должны оставаться побайтово неизменными. После частичного запуска 034 или 035 не удаляйте записи журнала и не меняйте SQL для обхода блокировки: сверяйте таблицы, enum, индексы и внешние ключи на восстановленной копии по исходному файлу, затем завершайте миграцию согласованным способом DBA. До успешного завершения остановите старые app/worker.

Для проверки после обновления создайте пустую комнату, войдите вторым пользователем, выйдите и войдите снова; проверьте приглашённую комнату и архив. Создайте выключенный черновик агента, протестируйте его, опубликуйте и отдельно проверьте узел согласования.
