# Контур Work 0.14.2

Исправлен конфликт `integration_connections` между миграциями 002 и 021. Это дефект поставки: 002 уже создаёт старую таблицу настроек, а 021 повторно использует её имя для несовместимой схемы проектных уведомлений. Исправление 0.14.1 обнаруживало конфликт, но не умело завершать такой переход.

## Изменения

- Мигратор распознаёт точную старую структуру 002 и сохраняет таблицу как `integration_connections_legacy_002`. Идентификаторы, строки, даты, JSON и шифротекст сохраняются без преобразования. Затем применяются исходные CREATE TABLE из 021.
- Проверяются схема, внешние ключи, индексы и отсутствие зависимых объектов, мешающих переименованию. Занятое имя сохранения не перезаписывается. Обрыв после RENAME или любого CREATE можно продолжить штатным запуском, с повторной проверкой.
- Диагностика `--status` показывает `recovery_021.legacy` и причины блокировки. Исходные файлы 001–029 и их контрольные суммы сохранены, новой SQL-миграции нет.
- Устранён запрос администрирования к отсутствующим столбцам старой схемы в новой таблице. Старые подключения отображаются отдельным перечнем в разделе интеграций, доступным с правом `integration.manage`; конфигурация и секреты не передаются браузеру.
- Уже успешно обновлённые установки без старой таблицы продолжают работать. Прежние подключения не превращаются автоматически в уведомления: проект, события и реквизиты для нового подключения нужно выбрать в каталоге.

## Обновление

Используйте [DATABASE-UPGRADES.md](DATABASE-UPGRADES.md#ошибка-021_integrationssql-прервана-er_table_exists_error). Для Compose замените код в существующем каталоге, сохранив `.env`, тома и имя проекта, соберите образ, остановите запись приложения/worker, выполните `--status`, миграцию и запуск приложения. При пустом `conflicts` состояние `legacy.state=rename_pending` ожидаемо и разрешает штатный переход. Ручное удаление таблиц/журналов или правка старого SQL не нужны.

Для Kubernetes образ 0.14.2 нужно собрать и загрузить в свой registry, обновить chart/image.tag и запустить миграционный Job с прежними секретами после остановки записи. Исправление само по себе не обновляет пользовательский сервер.

## Проверка

Регрессионные тесты охватывают исходную схему 002, все границы прерывания RENAME/CREATE, потерю ответа после завершённого переименования, занятую таблицу сохранения, неожиданные зависимости, несовместимую схему и загрузку администрирования. Проверяется список повторно используемых имён таблиц во всех миграциях, чтобы подобный конфликт больше не проходил незамеченным.

Итог локальной проверки: **199 тестов прошли**, проверка CSS/PWA/UI-контрактов и production-сборка Next.js завершились успешно. Модуль загрузки администрирования также проверен на импорт в Node.js для интеграционного сценария.

Изолированный MySQL-сценарий исправлен: он использует таблицу, действительно созданную 002, и сравнивает старые строки до и после восстановления. Отдельный сценарий чистой установки включает загрузку администрирования. Docker/MySQL в среде подготовки недоступны; эти сценарии подготовлены, но здесь не запускались. Перед production-обновлением проверьте их и копию своей БД.
