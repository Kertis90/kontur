# Поэтапный переезд с Jira

Раздел: **Администрирование → Импорт из Jira → Переезд с Jira**.
Рекомендуемый первый шаг — один небольшой пилотный проект. Подключение читает
Jira и не изменяет её задачи или настройки. Проекты можно переключать по очереди.

## Подключение собственного сервера

1. Создайте проект в Контуре, сотрудников, нужные этапы, типы и дополнительные поля.
   Настройте группы и доступы в Контуре до переноса содержимого.
2. Выберите «Подключить Jira», вариант **Jira Data Center / свой сервер**,
   адрес HTTPS (допустим путь `/jira`), ключ исходного проекта и проект назначения.
3. Введите персональный токен выделенного сотрудника Jira с правом чтения
   только нужных данных. Токен хранится зашифрованным и не возвращается браузеру.
4. Для внутреннего сервера добавьте его точное имя в
   `INTEGRATION_ALLOWED_PRIVATE_HOSTS` окружения приложения и worker.
   В Helm это `integrations.allowedPrivateHosts`. Настройка уже есть в обеих
   поставках. Проверка сертификатов HTTPS остаётся обязательной; корпоративный
   центр сертификации должен быть доверенным в окружении Node.js.
5. Нажмите «Получить данные для проверки». Дождитесь подготовки справочников,
   сопоставьте сотрудников, этапы, типы и поля, сохраните и повторите подготовку.
6. Просмотрите поля нескольких задач, ошибки и предупреждения. Подтвердите
   допустимые исключения и нажмите «Подтвердить перенос».

Контур должен иметь запущенный обычный worker, MySQL и приватное S3 для файлов.
Нового фонового сервиса и новых обязательных переменных окружения нет.
Доступ к настройке — через вход сотрудника в приложение: управление импортом,
администрирование выбранного проекта и чтение/изменение всех его полей.
Создание, изменение задач, назначения, вложения и связи проверяют свои права.
Токены API и служебные учётные записи агентов не настраивают перенос.

## Повторение и завершение

Повторное получение проходит весь выбранный проект страницами по 25 задач.
Стабильный идентификатор Jira сохраняет соответствие даже при смене ключа задачи.
Пауза и перезапуск worker сохраняют позицию; сетевые ошибки повторяются до пяти
попыток с задержкой, указанной Jira. После исправления причины можно продолжить.

Повторный перенос сравнивает предыдущий снимок, текущую задачу Контура и Jira.
Изменения разных полей объединяются. При одновременном изменении одного поля
задача попадает в конфликты: «Посмотреть поля» показывает обе версии. Выберите
сохранение полей Контура либо принятие полей Jira; решение относится к полям
всей задачи, а не к одному полю. Новая правка сотрудника после выбора снова
потребует проверки. История и файлы повторно не добавляются.

После задач выполняется общий проход связей, включая задачи следующих страниц.
Для связанных проектов того же сервера доступ к обоим проектам проверяется
отдельно. После переноса второго проекта нажмите «Повторно проверить связи».
Изменённые вручную родители и конфликтующие связи не перезаписываются.
Удаления задач, файлов, комментариев и связей в Jira не удаляют данные Контура.
Пропавшие из текущей выборки задачи отражаются в отчёте.

Перед переключением остановите изменения проекта в Jira, повторите перенос,
сверьте количество задач, файлы, связи и исключения, скачайте полный отчёт.
Ошибки, конфликты, недостающие файлы и связи блокируют переключение.
Введите ключ проекта и подтвердите «Команда переходит в Контур».
Подключение больше не принимает переносы; режим доступа в самой Jira меняет
её администратор. Обратный перенос изменений из Контура не выполняется.

## Границы текущего переноса

- Права, группы и корпоративный вход настраиваются отдельно. Задачи с уровнем
  безопасности Jira исключаются, комментарии с ограниченной видимостью также
  исключаются. Для полей, скрываемых сторонними расширениями Jira, используйте
  токен, которому доступны только разрешённые к переносу данные.
- Переносятся название, текст описания, этап, исполнитель, срок, приоритет,
  сопоставленный тип, простые дополнительные поля, оценки, комментарии,
  доступная история, файлы, поддержанные связи, родитель и эпик.
  Оформление описаний преобразуется в текст. Неизвестные приоритеты и поля,
  компоненты, версии, трудозатраты и метки перечисляются в предупреждениях.
  Конфигурация процессов, спринты, Confluence и плагины Jira не переносятся.
- Data Center использует `/rest/api/2` и персональный токен. История приходит
  через `expand=changelog`; если версия Jira возвращает её не полностью,
  неполнота отражается в сверке. Комментарии читаются постранично.
- Cloud использует `/rest/api/3/search/jql`, почту и API-токен, постраничные
  комментарии и историю. В обоих вариантах более 1000 комментариев/записей
  истории или ответ более 3 МБ останавливает подготовку, данные не обрезаются молча.
- Файлы скачиваются только с того же HTTPS-сервера и контекстного пути,
  без перенаправлений. Внешнее хранилище и перенаправляемые вложения, в том числе
  некоторые варианты Cloud, требуют прежнего импорта подготовленного экспорта.
  Размер ограничен `MAX_ATTACHMENT_BYTES`, дополнительно не более 100 МБ.
- Задачи, ранее перенесённые файловым импортом, автоматически не привязываются
  к серверу Jira: старый формат не сохранял его идентичность. Совпадение ключа
  блокирует прямой перенос в этот проект. Для пилота выберите чистый проект.
- Реальные версия, права, нестандартные поля и объём вашей Jira ещё требуют
  пилотной проверки. Автоматические проверки используют контролируемые ответы
  Jira и настоящие MySQL/S3, не подключаются к рабочему серверу пользователя.

Контракт доступен в `/api/openapi.json`. Настройка подключения и все действия
требуют актуальную версию записи; устаревшее изменение возвращает конфликт.
Справочники ограничены 1000 значениями каждого вида, подключения — 100 на
организацию. Старый [импорт из файла](JIRA-IMPORT.md) сохранён.

Справочные первоисточники: [Data Center REST](https://developer.atlassian.com/server/jira/platform/rest/v11002/api-group-search/),
[персональные токены](https://developer.atlassian.com/server/jira/platform/personal-access-token/),
[поиск Cloud](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/).
