# Тестирование, цели и поиск по смыслу

## Тестирование

Раздел «Тестирование» виден при наличии qa.view, qa.manage или qa.execute хотя бы в одном проекте. Просмотр не даёт права менять кейсы. qa.manage настраивает библиотеку и планы, qa.execute создаёт прогоны и записывает результаты. Для создания дефекта дополнительно нужен task.create, а по API — tasks:write.

Кейс содержит предусловия, пары «действие/ожидаемый результат», приоритет, automation_key и связанные задачи. Архивирование сохраняет историю. План выбирает кейсы и опциональный релиз того же проекта. При создании прогона фиксируются версии кейсов и релиз: изменение плана не переписывает прошлые проверки.

Результаты passed/failed/blocked/skipped/untested сохраняются с комментариями, исполнителем и версией. Прогон завершается после отметки всех кейсов и становится доступным только для чтения. Ошибку можно связать с существующей задачей или создать из результата.

### JUnit из CI

Установите automation_key кейса равным `classname.name` из JUnit. Создайте прогон вручную или через POST /api/work/quality/runs. Токен пользователя CI должен иметь quality:read, quality:write и проектное qa.execute.

```bash
python3 scripts/publish-junit.py \
  --file junit.xml --run-id 12 \
  --base-url https://projects.example.ru \
  --packet-file ci-result-checkpoint.json
```

Передайте полный токен в переменной KONTUR_API_TOKEN через секрет CI. Не сохраняйте его в отчёте. Скрипт допускает HTTPS, не следует перенаправлениям, отклоняет XML с DTD/entities и файлы больше 10 МБ. Неизвестный automation_key останавливает отправку.

Checkpoint сохраняет точное тело запроса и UUID до отправки. При сетевом сбое повторите команду с тем же файлом отчёта и checkpoint; сохраните checkpoint между повторами CI. Для другого отчёта создайте новый checkpoint. Повтор с другими результатами под прежним UUID отклоняется сервером. Текущий результат всего пакета и история меняются в одной транзакции.

## Цели и OKR

okr.view разрешает просмотр, okr.manage — настройку, okr.update — внесение замеров. Цель включает проект, владельца с доступом к нему и срок. Архивную цель нельзя изменять до возвращения в работу.

Ключевой результат бывает ручным числом или долей завершённых связанных задач. Для ручного задаются начало, цель, единица и вес. Поддерживается уменьшение показателя, например с 14 до 7 дней. Прогресс ограничен диапазоном 0–100%, фактическое число сохраняется без обрезания. Прогресс цели — взвешенное среднее результатов.

Каждый замер требует пояснения и состояния on_track/at_risk/off_track; история не заменяется последним значением. Право на внесение замера не позволяет менять цель или вес. Ссылки на задачи ограничены выбранным проектом.

## Семантический поиск

1. В «Администрирование → Искусственный интеллект» сохраните включённый профиль своего провайдера.
2. В блоке «Семантический поиск» выберите профиль и отдельную модель embeddings. URL профиля должен быть базовым HTTPS-адресом API, к которому добавляется `/embeddings`.
3. Дайте ответственному semantic.index, а пользователям поиска — ai.search.
4. Откройте «Планирование и инструменты → Поиск с ИИ → Управление индексом», запустите обновление.

Используется совместимый формат [embeddings API](https://developers.openai.com/api/reference/resources/embeddings/methods/create): model, input, encoding_format=float; ответ data с index/embedding и usage.prompt_tokens. Поддерживаются размерности 32–4096. Ключ берётся из профиля и не раскрывается браузеру. Для внутреннего HTTPS-сервера укажите точный хост в INTEGRATION_ALLOWED_PRIVATE_HOSTS; транспорт проверяет адреса DNS, не следует редиректам и блокирует служебные/loopback адреса.

Фрагменты доступных ответственному материалов отправляются провайдеру. Расход учитывается в общем месячном бюджете ИИ. Ошибки с неизвестным расходом сохраняют резерв. Текстовая генерация ответа — отдельный существующий режим; поиск по смыслу возвращает реальные фрагменты и ссылки.

Векторы зашифрованы в MySQL; LSH-таблица содержит номера групп кандидатов, не исходный текст. Перед выдачей читается актуальный источник и проверяются права проекта/пространства/записи, срок хранения и хеш текста. Изменённые или удалённые источники не показываются по старому индексу. Повторный проход обновляет изменённые материалы; прежние пространства индекса после смены модели больше не используются.

Один активный проход на рабочее пространство. Задание хранит позицию, переживает перезапуск worker и может быть остановлено/возобновлено. Для API нужны semantic:write и scopes всех трёх типов источников. Отзыв токена/прав останавливает фоновую обработку. При смене модели создайте новое задание.

Это приближённый поиск по ограниченным фрагментам, а не полный экспорт или исчерпывающий поиск всех совпадений. Для точного списка задач используйте обычный язык запросов.
