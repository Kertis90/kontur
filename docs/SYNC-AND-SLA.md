# Календари, синхронизация и SLA

## Календарь сотрудника

«Интеграции → Календари и синхронизация»: создайте личное CalDAV-подключение, задайте HTTPS URL коллекции, пользователя и пароль приложения, затем включите его. Требуется calendar.connect. Другие пользователи не получают доступ к его реквизитам и журналу.

Выберите запланированную встречу из доступных вам. Создаётся стабильный UID и объект `.ics` в выбранной коллекции. Перед первой записью применяется If-None-Match, при обновлении — ETag/If-Match. Переносятся название, описание, время, отмена и собственный ответ участника. Конфликт обеих сторон требует выбора пользователя. Параметры встречи может импортировать организатор или управляющий; RSVP относится только к текущему сотруднику.

Поддерживается одна неповторяющаяся встреча, UTC и TZID. События с сериями, floating time и вложенными компонентами не перезаписываются. Коллекция задаётся вручную; поиска существующих чужих событий и полного календарного клиента нет. Основа протоколов: [CalDAV](https://www.rfc-editor.org/rfc/rfc4791), [iCalendar](https://www.rfc-editor.org/rfc/rfc5545).

## GitLab

Для настройки нужны integration.manage и project.admin. Выберите проект Контура, базовый HTTPS URL GitLab, токен с доступом к Issues API, ID внешнего проекта и два этапа: рабочий/завершённый. Сопоставьте ID пользователей GitLab с ID сотрудников Контура. Один внешний и один внутренний пользователь на соответствие.

Свяжите существующую задачу с IID GitLab issue. Обмен включает название, описание, срок, одного исполнителя и состояние opened/closed. Несопоставленные промежуточные этапы или пользователи приостанавливают конкретную связь. При первом объединении разных версий выберите локальную или внешнюю.

Обработчик сравнивает обе стороны с предыдущим успешным снимком. Одновременные разные изменения требуют решения. Перед применением решения вновь проверяется хеш конфликта, после записи — равенство сторон. Пока идёт обмен, редактирование и удаление связей блокируются. Внешний [GitLab Issues API](https://docs.gitlab.com/api/issues/) не даёт используемой здесь атомарной гарантии сравнения и записи: узкое окно гонки со сторонними клиентами остаётся.

Удаление подключения или связи не удаляет внешнюю/локальную задачу. Отсутствие объекта снаружи вызывает конфликт. Все HTTPS-запросы ограничены по времени и размеру, проходят проверку DNS; реквизиты и конфликтные снимки зашифрованы.

## SLA и автоматизации

Настройте правило SLA и рабочий календарь, затем откройте блок уведомлений сохранённого правила. Выберите предупреждение/нарушение для исполнителя и список адресатов эскалации. escalation_minutes — рабочие минуты после истечения SLA, включая настройки выходных, праздников и пауз.

Фоновый проход обрабатывает до 500 активных задач в минуту с сохранением позиции. На большой базе задержка оповещения зависит от длины полного прохода. Завершённые и приостановленные таймеры уведомления не отправляют. Событие для одной версии правила/календаря и цикла дедуплицируется. При изменении настроек может появиться новое уведомление для новой версии.

Адресат должен быть активен, иметь доступ к проекту и атрибутам условий правила. Системные события sla.warning/sla.breached/sla.escalated можно использовать в конструкторе автоматизаций. Для действия integration_send нужны integration.send, automation.manage и доступ к подключению того же проекта; правило должно быть привязано к конкретному проекту. Предварительный просмотр показывает подключение и данные задачи, не выполняя отправку.

В журнале интеграции доступны состояние доставки и изменения конфигурации. Терминальная ошибка уведомляет последнего редактора подключения не чаще раза в час; успешная доставка после ошибки сообщает о восстановлении. Секреты в историю не записываются. Состояние подключений старого универсального webhook-модуля в этот новый журнал не включается.
