# Эксплуатация и восстановление

## Состояние платформы

«Администрирование → Состояние платформы» требует operations.view. Он показывает проверки чтения MySQL, Redis и S3, количество процессов worker/recording-worker с сигналом за последние 90 секунд и очереди рабочего пространства. Обновление — каждые 30 секунд. Присутствие процесса не означает успешного выполнения всех операций; следите также за возрастом очереди и журналами.

`GET /api/work/operations/metrics` использует персональный токен с operations:read, явно разрешённый политикой пользователя. Выделите техническую учётную запись с operations.view; не выдавайте ей остальные административные права. Секреты, тексты задач и имена сотрудников в метрики не включаются.

Для существующего Prometheus используйте [пример конфигурации](../deploy/monitoring/prometheus.example.yaml), [правила оповещений](../deploy/monitoring/kontur-alerts.yaml) и [панель Grafana](../deploy/monitoring/grafana-dashboard.json). Файл токена смонтируйте только для чтения. Метрики общих очередей повторяются на каждой реплике: для одного рабочего пространства агрегируйте max/min, не sum. Для нескольких рабочих пространств создайте отдельные scrape jobs и добавьте собственную метку workspace, затем разделите панели по ней.

Helm: установите Prometheus Operator, создайте Secret с ключом token в namespace приложения и задайте monitoring.enabled=true, monitoring.tokenSecret и labels, по которым ваш Prometheus выбирает ServiceMonitor. Если включена NetworkPolicy, задайте monitoring.namespaceSelector. Chart добавляет только ServiceMonitor; существующие Prometheus/Grafana не заменяются. Поля соответствуют [API Prometheus Operator](https://prometheus-operator.dev/docs/api-reference/api/).

## Зашифрованная копия MySQL

Нужны Node.js 22 и клиент mysqldump 8.4 либо Docker Compose с сервисом mysql. Копия использует single-transaction, quick, no-tablespaces, hex-blob, routines/events и set-gtid-purged=OFF. У пользователя резервирования должны быть необходимые права чтения, SHOW VIEW, TRIGGER, EVENT и просмотра процедур; для --pitr нужны дополнительные права получения координат/блокировки. Не запускайте параллельно DDL-миграции. Требования утилиты описаны в [документации MySQL](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html).

Задайте **отдельный** BACKUP_ENCRYPTION_KEY: 64 шестнадцатеричных символа. Сохраните его вне сервера резервных копий. Для подключения скрипт использует MYSQL_*; при локальном запуске можно передать MYSQL_DEFAULTS_FILE с настройками клиента и TLS. Пароль не добавляется к аргументам mysql/mysqldump, он передаётся через MYSQL_PWD.

```bash
mkdir -p backups
node --env-file=.env scripts/backup.mjs backup \
  --compose --output backups/kontur-before-update.kbk
node --env-file=.env scripts/backup.mjs verify \
  --input backups/kontur-before-update.kbk
```

Формат `.kbk`: gzip + AES-256-GCM, аутентифицированные метаданные, случайный IV и SHA-256 итогового файла. Существующий файл не перезаписывается. Неуспешный mysqldump не оставляет готовую копию. verify полностью проверяет шифротекст и распаковку, но не подтверждает возможность восстановления схемы MySQL.

Добавьте `--s3` для загрузки в отдельный BACKUP_S3_BUCKET через S3_ENDPOINT/S3_ACCESS_KEY/S3_SECRET_KEY. Bucket должен существовать и отличаться от основного bucket вложений. Сохраните идентификатор объекта и SHA-256 из JSON-результата. Настройте версионирование, срок хранения и копирование в отдельную зону средствами вашего S3. Ошибка загрузки оставляет локальный зашифрованный файл для повторной передачи.

SQL-копия не содержит файлов встреч, вложений, ключей шифрования и конфигурации. Резервируйте их отдельно. При согласованном восстановлении сначала остановите записи приложения, восстановите выбранный набор MySQL/S3/ключей, затем проверьте ссылки и права. Наличие архивного файла не является проверкой восстановления.

## Плановый запуск в Kubernetes

Chart содержит выключенный по умолчанию backup CronJob. Включите backup.enabled, задайте schedule, bucket, secretName и лимит workSize, достаточный одновременно для SQL и зашифрованного архива. По умолчанию job запускается в 02:00 UTC, запрещает параллельные запуски и имеет ограничение времени.

В отдельном Secret резервирования нужны MYSQL_USER/MYSQL_PASSWORD, BACKUP_ENCRYPTION_KEY, S3_ACCESS_KEY/S3_SECRET_KEY. Можно переопределить S3_ENDPOINT для отдельного хранилища. Доступ к исходной БД — через database.host/port/name. Для TLS по умолчанию используется VERIFY_IDENTITY; задайте database.ssl.ca для частного CA и DNS-имя, совпадающее с сертификатом.

Init-контейнер MySQL делает дамп на временный том; основной контейнер шифрует и загружает его. Незашифрованный промежуточный SQL доступен только контейнерам этого pod, том удаляется вместе с pod. Нужны успешный статус job и проверка объекта в S3. Эта job резервирует только MySQL и не выполняет восстановление автоматически.

## Учебное восстановление

Сначала проверьте архив через verify. Скрипт restore проверяет GCM **до** передачи SQL серверу. Он принимает только пустую БД `kontur_restore_*` на явно выделенном сервере; исходное имя из копии запрещено. При ошибке SQL не применяются следующие команды, но частично созданную учебную БД нужно считать непригодной.

Для отдельного Compose-проекта задайте RESTORE_MYSQL_PASSWORD, RESTORE_MYSQL_USER=root, RESTORE_MYSQL_DATABASE=kontur_restore_drill:

```bash
docker compose -f deploy/compose.restore.yaml up -d
# Дождитесь готовности MySQL, затем:
node --env-file=.env scripts/backup.mjs restore \
  --compose --input backups/kontur-before-update.kbk \
  --database kontur_restore_drill --isolated
```

Файл восстановления создаёт отдельную внутреннюю сеть без опубликованного порта. Для удалённого выделенного стенда задайте RESTORE_MYSQL_HOST/PORT/USER/PASSWORD и при необходимости RESTORE_MYSQL_DEFAULTS_FILE, запускайте без --compose. Хост должен отличаться от исходного MYSQL_HOST.

После восстановления проверьте схемы и журнал миграций, количество проектов/задач/учётных записей, определения triggers/definers, вход и роли на отдельном приложении. Подключите копию S3 и исходный APP_ENCRYPTION_KEY, проверьте открытие выбранной записи и вложения. Зафиксируйте длительность и выявленные ошибки: только такой прогон позволяет оценить RTO. Сценарий не переключает production и не удаляет его данные.

## Восстановление на момент времени (PITR)

Флаг `--pitr` сохраняет координаты binlog через mysqldump --source-data=2. Полная процедура дополнительно требует непрерывного внешнего архива бинарных журналов с момента копии. Одного флага или обычной ежедневной копии недостаточно.

Оператор определяет координаты последней подходящей копии, проверяет непрерывность binlog, восстанавливает копию на изолированном сервере и применяет журналы до выбранной позиции. Учитывайте различие имён БД учебного стенда и исходных событий; проверьте фильтрацию/переписывание имён до применения. Для событий с бинарными данными нужен mysql --binary-mode. Принципы и ограничения: [MySQL PITR](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html).

Архивация binlog, выбор позиции остановки и переключение production остаются операциями DBA. Они здесь автоматически не запускаются. Непрерывность архива и реальное восстановление на момент времени в текущем окружении не проверялись.
