# Конструктор ИИ-агентов · 0.21

Агент относится к одному проекту. Графический редактор сценария с пятью разделами: **Запуск → Источники → Сценарий → Модель и инструкции → Действия**. Доступны десять шаблонов: аналитик проекта, разбор Allure, контроль сроков, итоги встречи, анализ с проверкой, риски выше порога. Старые агенты продолжают работать без дополнительных шагов и новых разрешённых действий.

## Быстрый старт

1. В «Администрирование → ИИ» настройте свой OpenAI-совместимый endpoint, ключ, модель, размер контекста и бюджет. Используются существующие профили и шифрование ключей.
2. Назначьте права проекта пользователям или группам: `agent.view` — раздел, `agent.manage` — настройки, `agent.run` — запуск.
3. Создайте агента, выберите источники и профиль. На шаге «Источники» проверьте реальную выборку кнопкой предпросмотра: обращения к модели нет.
4. При необходимости добавьте шаги анализа, условия, фильтры и текстовые шаги. Для обычной сводки сценарий можно оставить пустым.
5. Выберите разрешённые действия и получателей. Сохраните агента выключенным и нажмите **Тест**. Тест обращается к модели, расходует токены и сохраняет предложения, но не выполняет их. Это ограничение проверяется сервером.
6. Посмотрите журнал: результаты каждого выполненного шага, итог, основания, уверенность, предупреждения, расход. При необходимости исправьте настройки.
7. Включите агента. Для режима подтверждения нужны `agent.approve` и права соответствующих действий. Выбранные предложения применяются одной транзакцией; остальные не выполняются. Повтор не дублирует изменения.

## Перемещение и стрелки

Карточки перемещаются мышью или касанием независимо от выбранной точки связи.
Начало перетаскивания отменяет незавершённое соединение; простой клик выбирает
блок. Отдельная кнопка позволяет отменить создание связи. Масштаб и панорамирование
не меняют порядок исполнения.

Стороны стрелок выбираются автоматически по расположению блоков. Нажмите на
связь (с клавиатуры — Tab, затем Enter), чтобы закрепить её выход и вход сверху,
справа, снизу или слева. «Автоматически» возвращает подстройку. Ветви «Да» и «Нет»
имеют отдельные точки. Положение и стороны сохраняются вместе с черновиком;
отмена и повтор изменений действуют и для них.

## Общие части сценария

В библиотеке можно сохранить текущий сценарий под своим названием, выпустить
его новую версию и вставить выбранную версию в агент того же проекта.
Вызов закреплён за версией: обновление общей части не меняет существующие агенты.
После вставки проверьте разрешённые действия и лимит обращений к модели у агента.

Права проверяются для проекта вызывающего агента. Все вложенные шаги используют
общие ограничения и согласования. Допустимо до трёх уровней вложения и 128 шагов
после раскрытия общих частей; циклические вызовы запрещены. Старые сценарии
без общей части работают по прежним правилам.

## Разбор и повтор запуска

В редакторе откройте «Проверка по предыдущему запуску», выберите запуск,
затем блок на схеме. Отображаются вход, результат, ошибка, выбранная ветвь,
длительность и расход токенов. Подробные входы доступны пользователям с правом
настройки агента; они хранятся зашифрованно. Большие входы сокращаются с явной
пометкой. Если провайдер не сообщил расход, интерфейс показывает это отдельно.

«Повторить без применения действий» использует сохранённый черновик либо
опубликованную версию и данные исходного запуска. Сначала сохраните правки
редактора. Источники должны оставаться доступны и сохранять версии; повтор
проверяет права заново, расходует бюджет и никогда не применяет предложения.
После завершения фонового задания обновите список и откройте новый запуск.
Старые запуски без сохранённых входов для такого повтора не подходят.

## Триггеры, параметры и расписания

| Режим | Настройки |
|---|---|
| По кнопке / API | Выполнение от текущего пользователя; `request_id`, необязательный `task_id` и `inputs` |
| По событию | `task.created`, `task.updated`, `task.due_soon`, `comment.created`, `quality.allure.imported` |
| Интервал | 15–10080 минут после сохранения / обработки предыдущего времени запуска |
| Ежедневно | Локальное время HH:mm и часовой пояс IANA, например `Europe/Moscow` |
| Дни недели | То же плюс дни: 0 — воскресенье, 1 — понедельник, …, 6 — суббота |

Часовой пояс можно взять из браузера. При переходе на летнее время несуществующее локальное время пропускается; повторённое осенью исполняется только в первое вхождение. Пропущенные во время остановки worker интервалы не воспроизводятся пачкой: обрабатывается текущее просроченное расписание и вычисляется следующее время. БД и процессы должны использовать UTC; пользовательский часовой пояс влияет только на календарное расписание.

Для Allure есть фильтр «только при ошибках»; сбор тестов ограничивается прогоном из события. «Только задача события» использует ID события, ручного запроса или предпросмотра. Для остальных типов источников событие не подставляет новые ID автоматически.

До 12 входных параметров: ключ латиницей, название, тип `string` / `number` / `boolean`, обязательность и значение по умолчанию. Неизвестные ключи, неверные типы и пустые обязательные значения отклоняются. Для событий/расписаний обязательным параметрам нужны defaults. Числовой ноль и `false` — полноценные значения.

Условия триггера проверяются **после сбора данных, перед обращением к модели**. Если они не выполнены, запуск завершается с пояснением без расхода токенов. Выберите «все» или «любое» из максимум 12 правил. Сравнения: равно, не равно, больше, меньше, содержит, заполнено, пусто. Число `2` не равно строке `"2"`.

События/расписания исполняются от последнего редактора. Если настройка сделана через API, сохраняется ID токена; срок, отзыв, scopes и политика пользователя проверяются перед каждым шагом и применением. Пауза работает даже при недоступном профиле модели или отозванных правах источников.

## Визуальный сценарий

| Шаг | Поведение |
|---|---|
| Анализ моделью | Собственный профиль или основная модель. Задание до 6000 символов. Вывод `summary` и до 10 полей `values` с заданными типами |
| Действие | Основная модель готовит предложения только выбранной операции. Учитываются разрешённые цели, общий лимит действий и режим подтверждения. Пропущенная ветвь не добавляет предложений |
| Условие | Выбирает переход «да» или «нет» по метрикам, параметрам или результатам предыдущих шагов |
| Фильтр источников | Оставляет указанные типы и первые N записей; пересчитывает метрики для последующих шагов |
| Собрать текст | Подставляет переменные в текст без вызова модели; результат доступен следующим шагам |
| Завершить сценарий | Сохраняет текст как итог без итогового вызова модели. Предложения уже пройденных блоков действий сохраняются для общей проверки и подтверждения |

До 32 шагов. Перемещение карточек не меняет порядок исполнения: его определяют
связи. Можно связать любые блоки, если не образуется цикл; несуществующие цели и
повторяющиеся ID запрещены. `flow.entry` задаёт первый шаг; по умолчанию это первый
блок списка. `$end` означает итоговый ответ. Пустой `next` сохраняет старое поведение
«следующий шаг по порядку». Условия используют отдельные `on_true` / `on_false`.

Библиотека позволяет добавить блок нажатием или перетаскиванием. Триггер, источники
и итоговая модель также перемещаются и выбираются для настройки. Связь задаётся
через выход карточки или список в настройках. Есть отмена/возврат изменений схемы,
автоматическое расположение, масштаб, вписывание и разворачивание карты. С клавиатуры
блок перемещается через Alt + стрелки. Кнопка «Сохранить схему» сохраняет черновик;
публикация рабочей версии остаётся отдельным действием.

У агента один основной способ автоматического запуска: события (можно выбрать
несколько) либо расписание. Ручной запуск остаётся доступным. Источники собираются
в одном входном блоке; фильтры внутри ветвей могут уменьшать дальнейшую выборку.

После обычного завершения цепочки основная модель формирует итоговую сводку.
Если в схеме есть блоки действий, предложения поступают только из пройденных
блоков и сохраняют порядок исполнения. Итоговой модели запрещено добавлять
действия вне этих ветвей. Сценарии прежних версий без блоков действий продолжают
получать предложения от итоговой модели.

Лимит `flow.max_calls` — 1–12; при сохранении он должен покрывать все блоки анализа
и действий плюс итоговый вызов, даже если ветви взаимоисключающие. Каждый вызов
учитывается в общих лимитах ИИ. Действия не применяются посередине схемы: сначала
проверяется весь результат, затем используются прежние правила подтверждения,
проверки актуальных прав и единая транзакция применения. Согласование сохраняет
уже подготовленные предложения и не вызывает прежние блоки повторно.

Примеры переменных:

```text
{{inputs.focus}}
{{metrics.overdue_count}}
{{trigger.event_type}}
{{steps.analysis.summary}}
{{steps.risk.values.score}}
{{steps.filter.count}}
{{steps.check.matched}}
```

Подставляются только скалярные значения. Пропущенный шаг или неизвестная переменная дают пустую строку. Нет выполнения JavaScript, рекурсивной подстановки или доступа к прототипам. Метрики: `source_count`, `task_count`, `overdue_count`, `critical_count`, `failed_tests`, `flaky_tests`. Они описывают **переданный контекст**, а не весь проект. Для просрочек выберите `due_date`: вместе с ним передаётся `is_done` из этапа; для критичности нужен `priority`.

Промежуточные результаты передаются последующим аналитическим шагам и итоговой модели. Фильтр сокращает последующие источники, но не стирает прежний анализ: права на все первоначально использованные источники продолжают проверяться. При превышении контекста промежуточными результатами запуск останавливается с пояснением; скрытого обрезания ответов шагов нет.

## Источники

| Источник | Выборка и доступ |
|---|---|
| Задачи | До 100; выбранные стандартные атрибуты, до 20 пользовательских полей с проверкой `fieldAccess`. Описание до 4000 символов |
| Фильтры задач | Этапы, приоритеты, исполнители, просрочки, задача события, текст в названии/описании, изменение за N дней |
| Комментарии задач | Последние 10 открытых, неудалённых; тело до 3000 символов. Внутренние комментарии исключены |
| Чек-лист задачи | Первые 30 пунктов |
| Тесты / Allure | До 10 завершённых прогонов и 20 результатов каждого; сводка Allure, до 20 flaky-тестов |
| Явно выбранные статьи | До 10; до 6000 символов каждой; права пространства, для черновика — редактирование |
| Пространства знаний | До 10 пространств; поиск по названию/содержимому, до 20 недавно обновлённых опубликованных статей |
| Переписка встреч | До 5 встреч проекта, по 50 последних сообщений; доступ к встрече и `ai.conference.summarize` |
| Чаты | До 5 выбранных чатов, по 50 последних сообщений, до 3000 символов каждого. Проектный чат должен быть этого проекта; закрытый — с членством исполнителя |
| Расшифровки записей | До 5 записей проекта с готовой расшифровкой; первые 20 фрагментов и до 16000 символов на запись. Требуются права просмотра записи и ИИ-изложения, срок хранения проверяется |
| Планирование | Последние 20 спринтов и 20 релизов проекта |
| Цели | До 20 неархивных целей и по 20 ключевых результатов; права OKR. Передаются сохранённые значения, без вычисления динамического прогресса задач |

Готовую расшифровку сначала создайте в карточке записи встречи. Конструктор не скачивает S3-файлы и не выполняет повторное распознавание. Нет чтения произвольных URL, бинарных вложений или секретов интеграций.

Каталог интерфейса ограничен: до 200 статей, чатов и активных пользовательских атрибутов, до 100 встреч и готовых записей. Поиск в списках локальный. Доступные ID вне списка можно передать через API; недоступные источники сервер отвергает.

Сбор идёт в порядке: задачи → тесты → статьи → встречи → планирование → цели → чаты → записи. Записи, не помещающиеся в бюджет контекста, пропускаются. `meta.omitted` сообщает об ограничении, но не является точным числом всех исключённых записей; фиксированные пределы таблицы действуют независимо. Параметры и инструкции тоже занимают контекст. Уменьшайте выборку/инструкции или увеличивайте размер контекста профиля. Предпросмотр и запуск собирают данные независимо, поэтому состав может измениться.

Опция скрытия email заменяет адреса в источниках перед передачей модели. Она не скрывает все персональные данные и не меняет инструкции, входные параметры или сохранённые исходные записи.

## Действия, проверки и права

| Действие | Дополнительный доступ / ограничение |
|---|---|
| Создать задачу | `task.create`, `tasks:write`; текущий проект, стандартный начальный этап |
| Комментарий | `comment.create`, `tasks:write`; задача должна быть в контексте |
| Изменить атрибуты | `task.edit`, `tasks:write`; только явно разрешённые поля |
| Перевести на этап | `task.edit`, `tasks:write`; список допустимых этапов, обычные проверки согласования |
| Назначить исполнителя | `task.assign` + `task.edit`, `tasks:write`; список допустимых активных пользователей проекта |
| Пункт чек-листа | `task.edit`, `tasks:write`; добавление к задаче из контекста |
| Черновик статьи | `knowledge:write`, право редактировать разрешённое пространство; публикации нет |
| Сообщение в чат | `chat:write`, доступ к разрешённому чату для записи |

Изменяемые поля: `title`, `description`, `priority`, `start_date`, `due_date`, `progress`, `estimate_minutes`. Назначение и этап вынесены в отдельные действия. До 20 предложений за запуск. Сервер отвергает неизвестные операции, лишние поля, неразрешённые цели и ссылки на источники вне контекста. Удаление, изменение прав и произвольные сетевые/кодовые инструменты отсутствуют.

Для подтверждения нужны `agent.approve`, права выбранных действий и доступ ко всем источникам. Исходный исполнитель также должен сохранить свои права и доступ. Изменение исходной задачи, статьи, включённых комментариев, переписки, расшифровки или версии агента блокирует устаревшее применение. Чек-листы и версии целей/ключевых результатов проверяются перед выполнением. Изменения задач проходят общий механизм проекта с версиями и согласованиями. Несколько изменений одной задачи в одном ответе последовательно используют новую версию; весь пакет атомарен.

`policy.min_confidence`, `require_citations`, `require_reasons` задают проверки качества. Если порог не достигнут или данных нет, **автоматическое применение заменяется ожиданием решения человека**. Уверенность — самооценка модели. Наличие ссылки и обоснования не подтверждает фактическую точность. Неверный ID источника — ошибка ответа, а не просто предупреждение.

Результаты доступны только читателям всех исходных материалов. После изменения/удаления включённых сообщений или расшифровки прежний вывод может быть скрыт. Общая строка журнала не содержит закрытого текста. При выборе действий учитывайте аудиторию: задача, комментарий, черновик или сообщение могут пересказывать сведения из закрытых источников пользователям целевого проекта/пространства/чата. Назначайте разрешённые получатели осознанно; по умолчанию новые агенты работают с подтверждением.

Права конструктора:

- `agent.view`: настройки, журнал, статистика; результаты дополнительно проверяют ACL источников.
- `agent.manage`: создание, изменение, пауза, копирование, импорт/экспорт, история/восстановление; отмена чужих запусков вместе с `agent.run`.
- `agent.run`: предпросмотр, тест, запуск, отмена своих запусков, своя оценка результата.
- `agent.approve`: решение по предложениям.
- `agent.automate`: настройка и выполнение автоматических действий.

Права назначаются существующими ролями пользователей и групп. Администраторы и владельцы следуют общей модели доступа приложения.

## Журнал, версии и перенос

Журнал показывает статусы `queued`, `running`, `review`, `completed`, `failed`, `cancelled`, `rejected`; есть фильтр и постраничная загрузка. Карточка запуска содержит шаги и их выводы, длительности, итог, предложения, источники, проверки, модель и расход. JSON-экспорт результата повторяет проверки доступа. Можно сохранить оценку 1–5 и комментарий; каждый пользователь видит свою оценку. Обучение модели по оценкам автоматически не происходит.

Статистика за 7/30/90 дней содержит количество запусков по статусам, токены, сообщённые провайдером, и наиболее используемых агентов. Включает тесты; это не финансовый отчёт. Отсутствующий или неизвестный расход не оценивается выдуманным числом.

История конфигурации заполняется при сохранении, публикации и паузе. Для существующих агентов исходная версия фиксируется при первом изменении после обновления. Показываются последние 100 версий. Восстановление создаёт новую версию, перепроверяет ссылки/права, назначает текущего редактора исполнителем и выключает агента; старые queued/running/review отменяются.

Копирование в интерфейсе открывает выключенный черновик. Экспорт определения содержит `format: "kontur.agent.v2"`, `name`, `config`, без ключей модели и токенов. Импорт создаёт выключенного агента. ID профилей, пользователей, этапов и источников относятся к текущей установке: при переносе их нужно заменить. Подготовленный пример: [examples/agents/reviewed-project.json](../examples/agents/reviewed-project.json).

## Фоновая работа и ограничения

Используется существующий `worker` и MySQL. Новых сервисов Compose/Helm не требуется. Опрос очереди/расписаний примерно раз в 15 секунд, по два агента параллельно на worker, с общими ограничениями ИИ. Несколько реплик сериализуют выполнение **одного агента** блокировкой в БД. Это не планировщик с точностью до секунды.

`queue_limit` — 1–20 незавершённых queued/running, по умолчанию 1. При заполнении новые автоматические события отклоняются с `last_error`, не откладываются. `cooldown_minutes` — 0–1440 между постановками автоматических запусков; ручные не блокируются этой паузой, но их время учитывается для последующего автоматического запуска. До 100 агентов проекта; до 20 ожидающих решений; `daily_limit` 1–100 запусков в сутки UTC, включая тесты и ошибки. До 12 модельных вызовов на запуск. Каждый вызов расходует общий дневной лимит пользователя и месячный бюджет ИИ.

Worker пишет heartbeat раз в 30 секунд. Отсутствие heartbeat 15 минут переводит running в ошибку. Неопределённо завершившийся запрос модели автоматически не повторяется, поскольку он мог быть оплачен. Сохранённые автоматические предложения могут применяться после перезапуска, если проверки качества и права всё ещё разрешают это. Отмена во время запроса может не отменить оплату; результат не применяется.

Полные исходные промпты отдельно не сохраняются; в БД остаются конфигурация, ссылки/метаданные источников, промежуточные выводы и результат. История пока без автоматического TTL. Резервное копирование должно включать новые таблицы миграции `033_agent_studio.sql`.

## API

Контракты опубликованы в «Мой API» и `/api/openapi.json`. Основные scopes: `agents:read`, `agents:write`, `agents:run`, `agents:approve`. Они не выдаются новым токенам по умолчанию. Нужны также scopes источников (`tasks:read`, `quality:read`, `knowledge:read`, `conference:read`, `chat:read`, `projects:read`, `objectives:read`) и действий. Генерация требует `ai:write`. Scope не заменяет право роли проекта или пространства.

| Метод | URL после `/api/work/` |
|---|---|
| GET / POST | `agents` — список / создание |
| GET | `agents/options?project_id=1`, `agents/analytics?project_id=1&days=30` |
| GET / PUT / PATCH | `agents/{id}` — чтение / изменение / пауза |
| POST | `agents/preview` — полная конфигурация + `inputs`, необязательный `preview_task_id` |
| POST | `agents/{id}/run`, `agents/{id}/test` — `request_id`, `inputs`, необязательный `task_id` |
| GET | `agents/{id}/runs?status=review&offset=0`, `agents/runs/{runId}` |
| POST | `agents/runs/{runId}/review`, `/cancel`, `/feedback` |
| GET | `agents/{id}/versions`, `agents/{id}/export`, `agents/runs/{runId}/export` |
| POST | `agents/{id}/restore` — текущий `revision` и восстанавливаемый `version` |
| POST | `agents/import` — `project_id` и `definition` из экспорта |

```sh
curl --fail-with-body -X POST \
  -H "Authorization: Bearer $KONTUR_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"request_id":"55e80e56-a7bc-4427-9df1-3bd9f6f5f4b1","inputs":{"focus":"Сроки релиза"}}' \
  https://kontur.example/api/work/agents/1/test
```

Параметр `focus` должен быть объявлен у агента; ID берите из своей установки. Новый UUID — новый запуск. Повтор с тем же UUID и параметрами возвращает прежний запуск; изменение параметров, режима теста или версии при том же UUID даёт 409. Ответ 202 содержит ID для опроса результата. Для внешних триггеров используйте этот аутентифицированный API; анонимного webhook нет.

Расширенная конфигурация описана валидаторами `src/lib/agent-schema.js` и `src/lib/agent-flow.js`; каталог API содержит работающие примеры запросов, а пример ниже в репозитории — полный импортируемый сценарий после замены локальных ID.


## Новые возможности 0.18

Редактор показывает сценарий на интерактивном canvas: блоки можно перемещать, соединять с другими шагами без циклов (с версии 0.20; раньше — только с последующими), масштабировать и просматривать по трассе выполнения. Узел **Согласование** сохраняет зашифрованное состояние запуска в MySQL. Назначенные согласующие возобновляют запуск с места остановки после перезапуска worker; истёкшее или отклонённое согласование закрывает запуск.

Черновик хранится отдельно от опубликованной версии. Кнопки «Сохранить черновик», «Тест черновика» и «Опубликовать» позволяют менять сценарий без остановки работающего агента. В разделе «Учётные записи агентов» администратор задаёт владельца, проектные и рабочие права, модели, типы источников, пространства, чаты, встречи и месячный бюджет. Служебная учётная запись не имеет пароля, cookie или API-токена и не наследует глобальную роль. Экстренное отключение останавливает все её запуски.

«Создать по описанию» делает один проверяемый черновик через выбранную модель. Генерация не публикует агент и не включает действия автоматически. «Лаборатория» хранит до десяти примеров, замораживает одну ACL-проверенную выборку и сравнивает до двух версий. Процент отражает только заданные детерминированные проверки; неизвестный расход токенов не оценивается.

В источниках доступен поиск по смыслу по выбранным пространствам. В предпросмотре он отмечается как отложенный, при рабочем запуске использует существующий ACL-проверенный индекс и сохраняет короткие цитаты. Результат до применения показывает поля «сейчас» и «после» и блокирует устаревшие версии задач.

Практические шаблоны 0.18: готовность релиза, контроль договорённостей встречи, аудит противоречий базы знаний и повторяющиеся ошибки тестов.
