# Инструкции для разработки Контур Work

Этот файл действует для всего репозитория. Начните с `START-HERE.md`,
`docs/HANDOFF.md` и `docs/DEVELOPMENT.md`. Здесь сохранены решения проекта,
чтобы продолжать работу в VS Code без доступа к прежней переписке.

## Продукт и согласованные ограничения

- Русскоязычная приватная self-hosted система управления проектами и знаниями.
- Основная БД — MySQL 8.4; не заменять её SQLite/PostgreSQL или памятью процесса.
- Поддерживать оба способа поставки: standalone Docker Compose и Kubernetes Helm.
- Service Desk и инцидент-менеджмент исключены из продукта.
- Права назначаются пользователям и группам; учитываются workspace, проекты,
  команды, пространства знаний, API, комнаты и функции конференций.
- Системные владелец/администратор сохраняют полный доступ к администрированию.
  Предметные правила членства комнат и конференций проверяются отдельно.
- Конференции запускаются сразу или планируются, без обязательного числа людей.
  Встречи около 1000 участников требуют профиля вебинара и нагрузочной проверки.
- Постоянная комната чата может существовать без участников. Выход последнего
  участника не удаляет комнату и историю. Закрытые комнаты требуют членства.
- Запись встречи опциональна, файлы приватны в S3; расшифровка кэшируется.
- ИИ использует настраиваемые endpoints/модели, права, бюджеты и согласования.
  Служебный пользователь агента не должен получать интерактивную сессию.
- Сохранять мобильную вёрстку, PWA, русский интерфейс и текущие красные акценты.

## Архитектура и точки входа

- JavaScript ESM, Node.js 22.13+, Next.js 16 / React 19; версии в lock-файле.
- `app/page.jsx`, `src/components/WorkHub.jsx` — интерфейс и разделы.
- `app/api/[[...path]]/route.js` — вход API; `src/lib/work-api.js` — диспетчер
  дополнительных API. Обновляйте соответствующий модуль `*api-docs.js` при
  изменении контракта; актуальный OpenAPI возвращает `/api/openapi.json`.
- `src/lib/db.js`, `permissions.js`, `auth.js`, `api-access.js`,
  `project-access.js` — БД, аутентификация и общие проверки доступа.
- `src/lib/work-*.js`, `agent-*.js`, `chat-rooms.js` — предметная логика.
- `scripts/worker.mjs` — очередь и фоновые работы; `scripts/recording-worker.mjs`
  — записи и расшифровка; `src/lib/events.js` — события/outbox.
- MySQL хранит данные, Redis/BullMQ — очереди, S3 — вложения, LiveKit — медиа.
- Стили в `app/*.css`; сохраняйте области селекторов, избегайте глобальных
  изменений `input`, `button`, `select`, которые ломают соседние разделы.

## Правила изменений

1. Сначала прочитайте затронутый код, тесты и документацию. Сохраняйте текущий
   стиль файла, не переформатируйте весь проект ради небольшой задачи.
2. Все миграции `001`–`035` уже входят в поставку и неизменяемы побайтово.
   Новые изменения схемы — следующий свободный номер (сейчас `036`). Не менять
   контрольные суммы, не удалять запись журнала для обхода ошибки. MySQL DDL
   может примениться частично: порядок восстановления в `docs/DATABASE-UPGRADES.md`.
3. Проверяйте workspace и предметный доступ на сервере при каждом чтении,
   скачивании и изменении; скрытие кнопки в UI не заменяет авторизацию.
   Для API учитываются scope токена, политика пользователя и RBAC совместно.
   Используйте параметры SQL вместо интерполяции пользовательских значений.
4. В фоновой работе, push, ИИ-источниках и скачивании файлов проверяйте актуальные
   права. Не полагайтесь только на права в момент постановки задания в очередь.
5. Не удаляйте проверки revision/idempotency, аудит, лимиты и маскирование
   секретов. Не отправляйте ИИ данные за пределами доступа исполнителя.
6. Секреты только в локальном окружении/Secret; `.env*` с реальными значениями,
   выгрузки БД, ключи и пользовательские записи не попадают в Git и архивы.
7. Учитывайте оба профиля запуска при добавлении переменных, workers и сервисов:
   `.env.example`, Compose, Helm, документацию. `compose.dev.yaml` — только для
   инфраструктуры локальной разработки, не production.
8. Не выполняйте seed/миграции/очистку на рабочей БД без задачи на её изменение.
   Обычный seed создаёт демонстрационный проект и восстанавливает bootstrap-owner;
   он не предназначен для сброса пароля существующего пользователя.
9. Не заменяйте реальные функции моками в поставке. В тестах используйте принятый
   `scripts/test-module-loader.mjs`; новые проверки должны проверять поведение.

## Проверки и завершение задачи

Из корня проекта после `npm ci`:

```bash
npm test
npm run quality
npm run build
git diff --check
```

Для узкой правки запускайте соответствующие тесты; для релиза — полный набор.
Тесты `scripts/*.test.mjs` не требуют живого MySQL. Интеграционные проверки
описаны в `docs/DEVELOPMENT.md` и запускаются на отдельной одноразовой БД.
Перед релизом с UI-изменениями проверьте браузер на десктопе и телефоне.
Если MySQL, браузер, LiveKit, Docker или Helm недоступны, прямо укажите,
что именно не проверено; успешный build не подтверждает работу этих сервисов.

Пользователь ожидает конкретный результат: что изменено, проверки, ограничения,
коммит/архив. Не объявляйте сайт развёрнутым без фактического запуска и проверки.
Выбор Git-сервера/ветки принадлежит владельцу; в переносимой копии нет обязательной
привязки к прежнему remote. Не публикуйте изменения в произвольный новый remote.
