# Нагрузочные сценарии конференций

Сценарии предназначены для выделенного стенда с тестовыми пользователями. Они не запускались в окружении разработки и не подтверждают ёмкость конкретного сервера. Реальная пропускная способность зависит от CPU, сети, кодеков, числа публикуемых дорожек, подписок, TURN и записи.

LiveKit распределяет комнаты между узлами, но **одна комната должна помещаться на одном узле**. Дополнительные реплики обеспечивают распределение разных комнат, а не суммирование мощности для одной. Для больших встреч используйте режим вебинара, ограниченное число выступающих и адаптивную подписку; это не предел общего количества подключающихся людей. См. [официальное описание нагрузочных тестов](https://docs.livekit.io/transport/self-hosting/benchmark/).

## Медиаканал

Установите LiveKit CLI и настройте отдельный именованный проект стенда согласно [документации CLI](https://github.com/livekit/livekit-cli#usage). Имя передаётся явно, чтобы не использовать проект по умолчанию. Утилита нагрузки читает сохранённые реквизиты CLI; скрипт их не печатает.

```bash
LOAD_TEST_ACK=staging LOAD_DURATION_SECONDS=900 \
  node scripts/load/livekit.mjs webinar kontur-staging loadtest-webinar
```

| Профиль | Публикуют | Подписываются | Назначение |
| --- | --- | --- | --- |
| webinar | 4 видео | 996 | 1000 синтетических участников, небольшое число выступающих |
| audio | 10 аудио | 990 | 1000 участников аудиовстречи |
| meeting | 50 видео | 50 | Более плотное взаимодействие; отдельный профиль |

Скрипт ограничивает длительность 30–3600 сек и требует имя комнаты `loadtest-*`. Таймер завершает нагрузку, но его успешное срабатывание не означает прохождение теста производительности: сохраните вывод CLI, метрики сервера и собственные критерии качества.

Запускайте генератор с отдельной машины с достаточными CPU, полосой и лимитом открытых файлов. Не измеряйте загрузку SFU и генератора на одном узле. Зафиксируйте версии сервера/CLI, модель CPU, сети, кодек, TURN и количество дорожек.

## API и постоянный чат

Файл application.k6.js использует [k6 ramping-vus](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/ramping-vus/): 50 → 250 → 1000 пользователей, удержание 10 минут, затем спад. Каждый пользователь опрашивает чат своей конференции раз в 5 секунд. Это отдельная проверка серверной части приложения, не эмуляция браузерного видео.

Подготовьте приватный JSON-файл с разными активными пользователями и полными токенами:

```json
[
  {"user_id":1,"token":"ПОЛНЫЙ_ТОКЕН_ПОЛЬЗОВАТЕЛЯ_1"},
  {"user_id":2,"token":"ПОЛНЫЙ_ТОКЕН_ПОЛЬЗОВАТЕЛЯ_2"}
]
```

Для 1000 пользователей нужны 1000 записей. Они должны иметь conference:read и право входа в выбранную тестовую конференцию. Для доступа по ссылке добавьте join_code в запись пользователя. Не коммитьте этот файл: users.json в каталоге сценариев исключён из Git.

```bash
LOAD_TEST_ACK=staging LOAD_BASE_URL=https://staging.example.ru \
LOAD_USERS_FILE=/secure/kontur-load-users.json LOAD_CONFERENCE_ID=12 \
LOAD_USERS=1000 k6 run scripts/load/application.k6.js
```

По умолчанию сценарий только читает. LOAD_WRITE_CHAT=true включает одно тестовое сообщение на 12 циклов от каждого пользователя; нужны conference:write и открытая тестовая конференция. При нескольких генераторах разделите пользователей между ними, чтобы один токен не представлял сотни людей. Не отключайте права и ограничители запросов ради прохождения теста.

## Критерии приёмки стенда

- API: <1% ошибок, p95 <1,5 сек — начальные пороги k6, при необходимости согласуйте свои SLO.
- Записывайте успешность подключения, задержку подключения и доставки чата, потерю пакетов, RTT, CPU и исходящий трафик SFU/TURN, использование Redis/MySQL и задержку очередей.
- Повторите отдельные прогоны с записью Egress, демонстрацией экрана, несколькими выступающими, переключением ролей и мобильными устройствами. Синтетическая нагрузка не подтверждает работоспособность камер, микрофонов или мобильной клавиатуры.
- На нескольких комнатах проверьте распределение. Отказ узла с активной комнатой проверяется как прерывание и повторное подключение; бесшовное продолжение одной комнаты не гарантируется.
- Сохраните конфигурацию, отчёты, графики и ограничения, при которых получен результат. До этого обозначайте поддержку 1000 участников как целевой сценарий, а не проверенную гарантию.
