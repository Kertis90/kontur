## Быстрый запуск standalone Docker

Требования: Docker Engine 24+ и Docker Compose v2.

```bash
cp .env.example .env
```

Создайте секреты и запишите их в `.env`:

```bash
openssl rand -base64 48   # AUTH_SECRET
openssl rand -hex 32      # APP_ENCRYPTION_KEY
openssl rand -base64 36   # LIVEKIT_API_SECRET
```

Обязательно замените `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `ADMIN_EMAIL` и `ADMIN_PASSWORD`. После этого:

```bash
docker compose up -d --build
docker compose ps
```

Система будет доступна по адресу [http://localhost:3000](http://localhost:3000), LiveKit — по `ws://localhost:7880`, консоль MinIO — по `http://localhost:9001`. Проверка состояния:

```bash
curl http://localhost:3000/api/health
```

При запуске отдельный одноразовый контейнер `migrate` применит миграции и создаст владельца с данными `ADMIN_EMAIL` / `ADMIN_PASSWORD`. Если такая учётная запись уже существует, seed восстанавливает ей системную роль владельца и активный статус — это защищает bootstrap-администратора от случайной потери доступа. Только после успешной подготовки запускаются `app` и `worker`. Worker обрабатывает автоматизацию, webhooks, импорт, расшифровку голоса и регламентные проверки сроков.

## Быстрый запуск Kubernetes HA

Подготовьте внешний MySQL 8, HA Redis и S3 bucket, отдельный пул публичных media-узлов, опубликуйте контейнерный образ, создайте Kubernetes Secret и заполните `values-ha.example.yaml`. Установка:

```bash
helm upgrade --install kontur-work deploy/helm/kontur-work \
  --namespace kontur-work --create-namespace \
  --values values-production.yaml \
  --atomic --wait --timeout 15m
```

Полная инструкция, состав Secret, TLS MySQL, обновление и диагностика описаны в [документации Helm chart](deploy/helm/kontur-work/README.md).

## Расширенная модель доступа

Базовая роль пользователя задаёт стартовый профиль. Системные роли «Владелец» и «Администратор» всегда имеют полный доступ к рабочему пространству и проектам. Для остальных пользователей поверх базового профиля можно создавать роли рабочего пространства и проектные роли, выбирать отдельные функции, назначать каждую роль напрямую пользователю или группе и ограничивать область действия. Проектная роль может действовать во всём пространстве, внутри группы проектов или только в одном проекте.

Если пользователь получает одну функцию через несколько назначений, разрешения объединяются. Явный `deny` имеет приоритет над `allow` для обычных ролей; системные владелец и администратор сохраняют полный доступ. Вложенная группа наследует назначения родительской группы; циклическая вложенность блокируется. Срок действия назначения позволяет выдавать доступ подрядчикам и временным командам без ручного отзыва.

В базе знаний действует дополнительный предметный слой. Пространство может быть доступно всему рабочему пространству либо только явно выбранным пользователям и командам. Уровни `view`, `edit` и `admin` определяют просмотр, работу со статьями и управление ACL. Руководитель команды управляет её составом и пространствами команды; глобальный `knowledge.manage` охватывает все команды и пространства.

## Настройка корпоративных подключений

После входа откройте **Администрирование**.

### Почта

В разделе **Почта** укажите SMTP-сервер, порт, учётные данные и адрес отправителя. Сначала сохраните настройки, затем нажмите **Проверить и отправить**. Пароль хранится в MySQL только в зашифрованном виде.

### LDAP / Active Directory

В разделе **Доменная авторизация** выберите LDAP и укажите:

- URL, например `ldaps://dc.company.local:636`;
- Base DN, например `DC=company,DC=local`;
- Bind DN сервисной учётной записи;
- фильтр пользователя — для AD обычно `(sAMAccountName={{login}})`, для каталога по почте `(mail={{login}})`.

После успешной проверки можно включить LDAP-вход. Не отключайте локальный вход до проверки доменной авторизации отдельной учётной записью.

### OIDC / SSO

Для Keycloak, Entra ID или Authentik укажите Issuer URL, Client ID и Client Secret. В провайдере зарегистрируйте callback:

```text
https://projects.company.ru/api/auth/oidc/callback
```

Точный callback показывается в интерфейсе. OIDC использует Authorization Code, PKCE, `state`, `nonce` и проверку подписи ID Token по JWKS.

## Публикация за HTTPS

В production установите `APP_URL=https://projects.company.ru` и разместите приложение за reverse proxy. Пример Caddy находится в [deploy/Caddyfile](deploy/Caddyfile), Nginx — в [deploy/nginx.conf](deploy/nginx.conf).

MySQL, Redis и S3 API MinIO не публикуются на хост и доступны только во внутренней сети Docker Compose. LiveKit публикует signal/ICE/TURN-порты; их точный список приведён в standalone-инструкции. Консоль MinIO в production закройте firewall.

## Резервное копирование

```bash
mkdir -p backups
docker compose exec -T mysql sh -c 'exec mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers "$MYSQL_DATABASE"' > backups/kontur-$(date +%F-%H%M).sql
```

Восстановление выполняйте только на остановленном приложении или в согласованное окно обслуживания:

```bash
docker compose stop app worker recording-worker
docker compose exec -T mysql sh -c 'exec mysql -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"' < backups/backup.sql
docker compose start app worker recording-worker
```

Вложения находятся в volume `minio_data`, а очередь Redis — в `redis_data`; включите их в политику резервного копирования вместе с MySQL.

## Чаты, конференции и голосовая расшифровка

Камера, микрофон, запись голоса, демонстрация экрана и установка PWA требуют HTTPS (исключение браузеров — `localhost`). Видеосвязь работает через LiveKit SFU и встроенный TURN: браузер публикует поток один раз, а медиасервер раздаёт его подписчикам. Кнопка **Начать сейчас** создаёт комнату и сразу открывает проверку устройств. В планировании нет количества участников: если сотрудники выбраны через поисковую модалку, встреча доступна приглашённым; если список пуст, любой авторизованный сотрудник с уникальной ссылкой может подключиться. Backend всё равно проверяет рабочее пространство, политику встречи и роль комнаты.

Для обычной командной встречи выберите **Интерактив**. Для аудитории около 1000 человек выберите **Вебинар** и оставьте число докладчиков небольшим: зрители подписываются на потоки, но не публикуют камеру и микрофон. Приложение не задаёт искусственный лимит подключений и не передаёт `maxParticipants` в LiveKit. Важное ограничение распределённого LiveKit: одна комната целиком размещается на одном media-узле, поэтому HPA добавляет ёмкость для других комнат, но не делит одну встречу между pod. Перед мероприятием обязательно проведите нагрузочный тест на том же типе узлов и сетевом пути.

Расшифровка включается через `STT_API_URL`. Worker отправляет аудио в OpenAI-compatible или локальный Whisper endpoint, сохраняет результат в MySQL и при следующих открытиях карточки возвращает готовый кэш без повторного распознавания. Ключ передаётся в `STT_API_KEY`; для локального сервиса он может быть пустым.

## PWA и мобильная работа

После публикации за HTTPS браузер предложит **Установить**. На iOS используйте Safari → «Поделиться» → «На экран Домой». Навигация превращается в нижнюю мобильную панель, канбан прокручивается по колонкам, а карточки, чат, запись голоса и конференции адаптированы под touch-интерфейс. Service worker не кэширует API и персональные ответы.

## Интеграционный API

Администратор задаёт доступ в **Администрирование → Доступ к API**, а пользователь выпускает токен в **Мой API**. Секрет показывается только один раз. В этом же разделе доступны поиск по методам, раскрываемые примеры cURL и ссылка на OpenAPI 3.1. Пример запроса:

```bash
KONTUR_TOKEN="ВСТАВЬТЕ_ПОЛНЫЙ_ТОКЕН"

curl --request GET \
  --url "https://projects.company.ru/api/search" \
  --header "Authorization: Bearer $KONTUR_TOKEN" \
  --get \
  --data-urlencode "q=assignee = currentUser() ORDER BY priority"
```

На каждом запросе проверяются три слоя: scope токена (`tasks:read`, `chat:write`, `conference:write`, `telephony:write` и другие), разрешённые scope политики пользователя и действующие функциональные права/членство в проекте. Старые scope `collaboration:read/write` автоматически преобразуются в раздельные права чата и конференций. Отключение API-политики блокирует все токены пользователя немедленно. Webhooks подписываются заголовком `X-Kontur-Signature-256: sha256=...`.

- OpenAPI: `GET /api/openapi.json`;
- полная таблица методов, примеры и контракт телефонного шлюза: [docs/API.md](docs/API.md).

## Разработка

Полный порядок настройки локальной MySQL/Redis/S3, `.env` и задач VS Code —
в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md). `.env.example` предназначен для
Docker-сети, `.env.development.example` — для приложения на компьютере разработчика.
Скрипты миграций/worker запускаются с `node --env-file=.env`; Next.js загружает
окружение самостоятельно.

Production-сборка:

```bash
npm run quality
npm run build
npm start
```

Команда `npm run check` последовательно проверяет читаемость типографики, целостность CSS, PWA-манифест и UI-контракты, а затем собирает production-версию.

Внутри ChatGPT Work для локальной проверки сборки требуется полифилл системного счётчика памяти:

```bash
NODE_OPTIONS="--require=$PWD/scripts/sandbox-memory-polyfill.cjs" npm run build
```

В обычном Linux/Docker этот полифилл не нужен.

## Структура

```text
app/                         интерфейс, стили и единый API Next.js
src/components/              planning, дашборды, коммуникации, отчёты и admin
src/lib/                     MySQL, RBAC, поиск, очередь, storage и automation
scripts/migrations/          версионируемые миграции MySQL
scripts/migrate.mjs          исполнитель миграций
scripts/seed.mjs             начальная конфигурация
scripts/worker.mjs           BullMQ worker, outbox, импорт, speech-to-text и регламентные события
compose.yaml                 standalone: app + worker + MySQL + Redis + MinIO + LiveKit/TURN
Dockerfile                   production-образ
deploy/standalone/           эксплуатация Docker Compose на одном сервере
deploy/helm/kontur-work/     Helm chart для отказоустойчивого Kubernetes
deploy/                      примеры reverse proxy
```

## Границы текущей версии

Это самостоятельная рабочая платформа и сильная основа для замещения Jira. Перед массовым production-запуском проведите нагрузочное тестирование на своём профиле данных, настройте внешний мониторинг и резервное копирование, проверьте LDAP/OIDC/SMTP с корпоративными серверами и выполните пилотную миграцию Jira на копии данных.
