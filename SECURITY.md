# Безопасность

## Перед production-запуском

- используйте случайные `AUTH_SECRET` и `APP_ENCRYPTION_KEY`;
- храните `.env` с правами `0600` или перенесите значения в Docker Secrets / секрет-хранилище оркестратора;
- измените пароль первоначального владельца;
- включите HTTPS и укажите публичный origin в `APP_URL`;
- оставьте MySQL без опубликованного порта;
- используйте LDAPS или StartTLS, проверяйте сертификат LDAP;
- для SMTP применяйте отдельный пароль приложения;
- ограничьте срок жизни и права OIDC Client Secret;
- регулярно проверяйте журнал аудита и резервные копии.
- публикуйте LiveKit только через доверенный TLS-сертификат, включите TURN/TLS и держите `LIVEKIT_API_SECRET` в секрет-хранилище;
- не передавайте записи голоса во внешний STT без согласованной политики обработки персональных данных.

## Модель защиты

- пароли локальных пользователей хешируются bcrypt с cost 12;
- сессия — подписанный HS256 JWT в `HttpOnly`, `SameSite=Lax` cookie;
- изменяющие запросы проверяют `Origin` относительно `APP_URL`;
- административные маршруты проверяют отдельные функциональные разрешения, назначаемые ролям и группам;
- изменение задач требует глобальной роли управления либо членства в проекте;
- интеграционные секреты шифруются AES-256-GCM;
- OIDC использует PKCE, state, nonce и проверку JWT по удалённому JWKS.
- API проверяет scope токена, политику пользователя и RBAC, а секрет токена хранится только как SHA-256 hash;
- сообщения и расписание конференций хранятся в MySQL, файлы и голос — в приватном S3 bucket; backend выдаёт ограниченный длительностью встречи LiveKit JWT с ролью комнаты, а WebRTC-медиа проходит через выделенный SFU/TURN, не через app pod.

Сообщения об уязвимостях передавайте владельцу конкретного развёртывания по внутреннему защищённому каналу. Не размещайте секреты или данные пользователей в публичных issue-трекерах.
