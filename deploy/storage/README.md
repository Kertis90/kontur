# Сборка файлового хранилища

Compose собирает MinIO и клиент `mc` из официальных исходников. Готовые образы
прежних выпусков перестали загружаться из Docker Hub и Quay при проверке 0.21.
Версии сервера и клиента сохранены; формат данных и настройки S3 не меняются.
Helm использует внешний S3 и не разворачивает MinIO.

| Компонент | Выпуск | Коммит исходников |
| --- | --- | --- |
| Сервер | RELEASE.2025-09-07T16-13-09Z | `07c3a429bfed433e49018cb0f78a52145d4bedeb` |
| Клиент | RELEASE.2025-08-13T08-35-41Z | `7394ce0dd2a80935aded936b09fa12cbb3cb8096` |

Dockerfile получает архивы из официальных репозиториев
[minio/minio](https://github.com/minio/minio/tree/07c3a429bfed433e49018cb0f78a52145d4bedeb)
и [minio/mc](https://github.com/minio/mc/tree/7394ce0dd2a80935aded936b09fa12cbb3cb8096).
Для каждого архива задан SHA-256: изменение содержимого остановит сборку.
Модули Go дополнительно проверяются по `go.sum`. Лицензии исходных проектов
сохраняются в `/usr/share/licenses` готовых образов.

## Первый запуск

Обычная команда из корня проекта собирает и приложение, и хранилище:

```bash
docker compose up -d --build --wait
```

Первой сборке нужны доступ к GitHub, реестру базовых образов, репозиториям Debian
и модулям Go, свободная память и несколько дополнительных минут. Последующие
сборки используют кэш Docker. Отдельная сборка только хранилища:

```bash
docker compose build minio minio-init
```

## Собственный реестр или закрытый контур

Соберите оба образа в среде с доступом к исходникам и опубликуйте их в своём
реестре. Укажите `MINIO_IMAGE` и `MINIO_CLIENT_IMAGE` в `.env`, затем загрузите
образы командой `docker compose pull minio minio-init`. Для такого запуска
используйте `docker compose up -d --no-build --wait` вместе с готовым образом
приложения. Параметры сети, бакета и реквизиты остаются прежними.

Исходники не включаются в контекст приложения: отдельный контекст сборки —
`deploy/storage`. Копирования `.env`, пользовательских файлов и базы в образы нет.
Обновление образа не требует удаления тома `minio_data`.

## Зеркала источников

Если собирать нужно на месте, адреса внешних источников задаются параметрами
в `.env` или через `--build-arg`. Все они необязательны: без них используются
публичные адреса.

| Параметр | Что перенаправляет |
| --- | --- |
| `DEBIAN_MIRROR`, `DEBIAN_SECURITY_MIRROR` | пакеты Debian |
| `GO_PROXY`, `GO_SUMDB` | модули Go |
| `ARCHIVE_BASE` | исходники с `codeload.github.com` при прозрачном прокси, сохраняющем пути |
| `MINIO_SOURCE_URL`, `MC_SOURCE_URL`, `MINIO_SOURCE_SHA256`, `MC_SOURCE_SHA256` | полные адреса, если архивы выложены под своими именами |

Для образа приложения отдельно задаются `NPM_REGISTRY` и `ALPINE_MIRROR`.

Зеркало Debian указывайте по `http`. Стадия `runtime` сама устанавливает
`ca-certificates`, и до этого момента в образе нет корневых сертификатов: адрес
по `https` с внутренним УЦ остановит `apt-get update` ошибкой проверки сертификата.
Целостность обеспечивают подписи GPG, поэтому и сам Debian раздаёт репозитории
по обычному http. Файл репозиториев переписывается в формате deb822, подпись
остаётся дебиановской — зеркало должно быть точной копией репозитория.

Архивы исходников копируйте побайтно: SHA-256 сверяется до распаковки. Архив тех
же коммитов, пересобранный другим сервисом (GitLab, Gitea), даст другую сумму и
остановит сборку. Надёжный путь — один раз скачать эти два файла как есть и
положить на внутренний файловый хост без изменений: тогда меняется только адрес,
а проверка продолжает работать. Если архив всё же пересобран, проверьте его сами
и задайте `MINIO_SOURCE_SHA256` / `MC_SOURCE_SHA256`.
